PR task/scifi_pp -> main : riepilogo cambiamenti (common_scripts + pixel_scripts)
====================================================================
sequencer_scripts/, submodule common_scripts e pixel_scripts, entrambi
sul branch task/scifi_pp (34 commit ciascuno sopra main). Rivisto
insieme in sessione il 2026-08-24, file per file, prima di aprire la PR.
scifi_scripts (terzo submodule, stesso branch) NON e' incluso in questa
PR - alcuni file di common_scripts sono comunque gia' consumati da
scifi_scripts, indicato dove rilevante.

Tema di fondo: common_scripts viene "flattato" (common/xxx/ -> xxx/ in
root, setup+folders in config/) e generalizzato da codice pixel-only a
codice condiviso pixel/scifi. pixel_scripts viene poi migrato per usare
queste classi condivise al posto delle sue implementazioni locali,
duplicate, che vengono rimosse.

NOTA (aggiunta dopo, stesso giorno): le sezioni COMMON_SCRIPTS e
PIXEL_SCRIPTS qui sotto descrivono lo stato SUBITO DOPO la migrazione
iniziale (common_scripts contiene ancora le classi PixelX/SciFiX).
Un rework successivo, descritto nella sezione finale "DIFFERENZIAZIONE
CLASSI PIXEL/SCIFI", ha spostato quelle classi FUORI da common_scripts
e dentro pixel_scripts/scifi_scripts rispettivamente - quindi frasi
come "PixelSetup in common/config/setup.py" o "operation/lifecycle.py"
sotto sono storiche, non lo stato attuale. Leggere l'ultima sezione per
la struttura vera e propria oggi.

COME FUNZIONANO I SALVATAGGI (SCIFI) - discusso il 2026-08-24
====================================================================
Tre canali di salvataggio distinti e indipendenti, attivati in momenti
diversi. Vale per common_scripts/results/saver.py +
scifi_scripts/calibrations/calibrationfactory.py.

1. Step-log dell'operazione (sempre attivo, solo locale)
--------------------------------------------
- Ogni Action/Calibration (OperationBase.__init__ in
  operation/lifecycle.py) crea un ResultSaverMultiple con solo
  has_local_result=True (niente ODB, niente ROOT/CDB a questo livello).
- Ad ogni append_step_result_and_check() durante prepare()/execute()/
  finalise() (stato power, letture, Final_Result finale) viene scritta
  una riga JSON in append su un file .ndjson locale:
    Action      -> scifi_scripts/output_actions/<NomeAction>_<N>.ndjson
    Calibration -> scifi_scripts/output_calibrations/<NomeCalib>_<N>.ndjson
  <N> e' un numero progressivo (ResultSaverLocal.
  get_last_execution_number() scandisce la cartella e prende il max+1).
- E' il "diario" tecnico di ogni singola esecuzione, sempre scritto
  indipendentemente da tutto il resto.

2. Risultato fisico della calibrazione (opt-in via ODB)
--------------------------------------------
- Solo per le calibrazioni vere e proprie (ScanThr, ScanVbr, PllTest),
  invocate dagli script del sequencer (scripts/thr_run.py, vbr_run.py,
  pll_run.py) tramite CalibrationFactory.run_calibration_and_save().
- Dopo che calib.run() ha prodotto lo step-log del punto 1, questa
  funzione legge dall'ODB due flag sotto il CAL_ODB_BASE della
  calibrazione (es. /CosmicRun/Calibration/SciFi/ScanThr/save_to_root,
  .../make_plots):
    save_to_root=True -> calib.build_root_report() scritto come file
      ROOT (uproot) in
      scifi_scripts/output_root/<report_name>_<run_number>.root.
      Se il file per quel run esiste gia', merge riga per riga
      (row_keys per calibrazione, upsert per chiave) invece di
      sovrascrivere - run incrementali.
    make_plots=True -> calib.build_plots() produce figure matplotlib
      salvate come PNG, una cartella per run, in
      scifi_scripts/output_plot/<report_name>_<run_number>/<entry>.png.
    save_to_cdb (parametro pySequencer, non ODB) True E save_to_root
      True -> il .root appena salvato viene caricato via HTTP al
      server CDB (http://mu3edb0/detcal, ResultSaverCDB). Se
      save_to_cdb e' richiesto ma save_to_root e' spento, non c'e'
      nulla da caricare e viene segnalato come errore in sequenza.

3. Stato/risultati live in ODB (indipendente da ResultSaver)
--------------------------------------------
- Ogni calibrazione (Thr/Vbr/Pll) scrive anche direttamente in ODB,
  ad-hoc (non passa da ResultSaver), i propri risultati/stato sotto il
  suo CAL_ODB_BASE (es. .../ScanThr/<folder>/ThrResult, .../Warnings,
  status Running/Done/Aborted).
- E' il canale che la pagina di controllo/monitoring legge in tempo
  reale, separato dai file ndjson/ROOT.

NOTA: esistono due strade di invocazione per le calibrazioni.
CalibrationFactory.perform_calibration() (dispatch da ODB
/CosmicRun/Calibration/SciFi/CurrentCalibration) fa SOLO il canale 1
(step-log locale) - non passa mai da run_calibration_and_save, quindi
non produce ROOT/plot/CDB. Le due strade coesistono nel codice attuale;
se sia voluto o se andrebbe unificato e' una domanda aperta, non
approfondita in questa sessione.


====================================================================
DIFFERENZIAZIONE CLASSI PIXEL/SCIFI - rework fatto lo stesso giorno,
DOPO tutto quanto sopra (stato ATTUALE della struttura)
====================================================================
Motivazione (utente): common_scripts conteneva sia le classi generiche
sia le loro sottoclassi PixelX/SciFiX - le seconde non c'entrano niente
con "common" e vanno nei rispettivi repo. Inoltre, dentro pixel_scripts
e scifi_scripts stessi, diverse classi/funzioni avevano nomi identici
tra i due repo (non e' un conflitto Python reale, i due repo non stanno
mai sullo stesso sys.path insieme, ma e' comunque confuso da leggere) -
richiesto di differenziarle con prefisso Pixel/SciFi ovunque avesse
senso. scifi_scripts e' quindi entrato a pieno titolo nello scope di
questo lavoro, anche se resta formalmente una PR separata.

1. Split common_scripts -> pixel_scripts/scifi_scripts
--------------------------------------------
Tutte le classi PixelX/SciFiX che stavano in common_scripts sono state
spostate nei rispettivi repo. common_scripts oggi contiene SOLO le
classi generiche (Setup, Folders, OperationBase/ActionBase/
CalibrationBase, DAQBase/DAQSCReads/DAQSCReadsArray, PowerPartitionBuilder,
OperationParameters). Verificato con grep: "^class Pixel\|^class SciFi"
su common_scripts -> zero risultati.

- operation/lifecycle.py rinominato operation/operation_base.py (come
  richiesto esplicitamente) - contiene solo OperationBase/ActionBase/
  CalibrationBase, senza le sottoclassi Pixel/SciFi.
- config/setup.py: PixelSetup/SciFiSetup rimossi, resta solo Setup.
- config/folders.py: PixelFolders/SciFiFolders rimossi, resta Folders
  + gli helper subsystem_root()/make_output_folder().
- daq/control.py: tutte le PixelDAQ*/SciFiDAQControl rimosse, resta
  DAQBase/DAQSCReads/DAQSCReadsArray.
- operation/operation_parameters.py: PixelOperationParameters rimossa,
  resta OperationParameters.
- power/partition.py: PixelPowerPartition(Builder)/SciFiPowerPartition
  Builder rimosse, resta PowerPartitionBuilder.
- Test di common_scripts (test_config.py, test_daq.py, test_operation.py,
  test_partition.py) riscritti per testare solo la parte generica.

2. pixel_scripts - nuovi file, alla stessa posizione che avevano prima

3. pixel_scripts - classi/funzioni rinominate per differenziarle da
