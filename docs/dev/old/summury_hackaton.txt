====================================================================
Written for whoever set up pixel_scripts/common_scripts originally (you

0. CONTEXT
----------

approach. Goal: shared scripts/ODB structure between scifi and pixel
where it genuinely overlaps, but two separate custom mhttpd control pages
(one per subdetector). A parallel, still-undecided effort

This document covers only the `common_scripts` / `pixel_scripts` work:
what got promoted to `common/`, why, what was explicitly NOT promoted and
why, two bugs found (one fixed, one left alone), and what's still open.

2. THE common/ PROMOTION RULE THAT WAS APPLIED
-----------------------------------------------
Same rule already documented in scifi-userfiles/README.md's "Rules for
this repo" section (reused verbatim as the working principle here):
`common/` is for code that is genuinely IDENTICAL everywhere it's used
TODAY, not code that "will probably be reused." Nothing gets promoted on
a guess - only once a second real caller needs the exact same code. This
was applied strictly throughout, including to things that "felt" generic
but had no confirmed second caller yet (see section 5).

3.1) common/odb.py
  Moved pixel_scripts/utils/odb.py here verbatim (that file no longer
  exists in pixel_scripts). Contains: `ODBCommandType` (enum: WRITE/READ/
  WRITE_AND_READ), `ODBCommand` (the general write/read/wait-for-ack
  primitive - takes a client, a command type, an ODB key, a value or
  value-producing callable, optional wait_key/wait_condition/max_wait_time
  for the "write then poll until a condition on another key flips" case),
  `ODBBooleanCommand` (specialization: write True, wait for the same key
  to revert to its original value - the "trigger a command bit and wait
  for the frontend to flip it back" pattern), `ODBSelection` (wraps a
  boolean ODB key read once at construction, for user-selection masks),
  and `find_channel_number_from_power_partition_name()` (looks up a
  channel index by searching a `Names` array under
  `/Equipment/<name>/Settings/<subfolder>` for an exact match).
  Zero pixel-specific content - no hardcoded equipment names or paths
  anywhere in this file.

3.2) common/setup.py
  Three execution-mode flags that used to live mixed into
  pixel_scripts/globals/setup.py alongside pixel-specific settings:
  `is_odb_available`, `can_send_commands_to_odb`, `run_from_sequencer`.
  These are read by common/odb.py's `ODBCommand.execute()` (to decide
  whether to hit real ODB or fall back to the `odb_write_test`/
  `odb_read_test` print-only stubs) and by common/power_supply.py's
  `PowerSupply.initialise_by_power_partition_name()`. Moving odb.py to
  common/ without moving these too would have created a real bug: code
  that sets `globals.setup.is_odb_available = X` (e.g.
  pixel_scripts/scripts/run_calibration.py, several of the test*.py
  scripts) would silently stop affecting what odb.py actually reads,
  because they'd be two different module objects holding two different
  copies of the same flag. Fixed by making common.setup the single
  source of truth and updating every caller (see section 4 for the full
  file list) to import common.setup instead of globals.setup wherever
  only these 3 flags were needed. pixel_scripts/globals/setup.py keeps
  only the pixel-specific fields (`odb_entry_path`, `read_febs_from_odb`,
  `read_power_partitions_from_odb`, `power_distribution_equipment_name`,
  `lv_supply_equipment_name`, `hv_supply_equipment_name`).

3.3) common/power_supply.py
  Went through two rounds today.

  Round 1: moved the `PowerSupply` base class (equipment_name/
  equipment_path/client bookkeeping, `initialise_by_power_partition_name`,
  `intialise_commands`/`is_initialized`, `read_all`, the reads-completeness
  check) plus `ODBPowerSupplyReadCommand` and
  `ODBPowerSupplyReadAndCheckCommand` (both `common.odb.ODBCommand`
  subclasses - the first auto-populates `ps.readables[key]` on read, the
  second additionally runs a caller-supplied `check_func` and populates
  `ps.readables_check[key]` with a pass/fail + message). At this point the
  concrete supply types (DCDC/HVboxN/MPDC) and the Factory stayed in
  pixel_scripts, deliberately NOT moved yet - no confirmed identical ODB
  paths on the scifi side at that point.

  Round 2 (explicit user request, after confirming the criterion should be
  "usable by both scifi and pixel", not just "already called by both"):
  moved `LVPowerSupply`, `HVPowerSupply` (the readables-declaring category
  classes) and the concrete `DCDCPowerSupply`, `HVBoxNPowerSupply` classes
  too. Justification, verified against real code (not just equipment
  names): pixel_scripts/globals/setup.py has
  `lv_supply_equipment_name = "DCDCCrates"` and
  `hv_supply_equipment_name = "HV"`. Read the actual
  scifi-userfiles/scripts/lv_power.py and hv_power.py source - they talk
  to `/Equipment/DCDCCrates/Settings|Variables/...` and
  `/Equipment/HV/Settings|Variables/...`, the SAME shared, unsplit
  (no Labor/Fibre variant) equipment trees. DCDCPowerSupply/
  HVBoxNPowerSupply just build ODBCommand objects addressing one channel
  of those trees by index - nothing pixel-topology-specific inside them.

  Deliberately NOT moved: `PowerSupplyType` (enum), `LVPowerDistribution`,
  `MPDCPowerSupply` (power-distribution concept - no confirmed scifi
  equivalent, scifi's dry-run findings never mentioned anything like
  PowerDistStaging/MPDC), and `PowerSupplyFactory` (it directly
  instantiates PowerSupplyType.MPDC's pixel-only branch, so it can't move
  without either moving MPDC too or splitting the factory - not done).
  These four all still live in pixel_scripts/core/power_supply.py, now
  importing `common.power_supply as base_ps` for the base class/read
  commands they still need.

  Type hints on `supply_type` parameters were dropped (was
  `supply_type: PowerSupplyType`) in the moved classes, since
  `PowerSupplyType` itself stays pixel-only and common/ can't reference
  it - this is a documentation-only change, no behavioral effect (Python
  doesn't enforce annotations at runtime here).

3.4) common/command_mixin.py (new)
  `CommandMappable` - `execute_command(name, *args)` (looks up name in
  `self.commands`, calls `.execute(*args)`, returns the real result) and
  `map_commands_to_self()` (turns every key in `self.commands` into a
  same-named bound method on the instance, e.g. so `ps.turn_on()` works
  instead of `ps.execute_command("turn_on")`).
  Extracted because this exact pattern was duplicated ALREADY 3 times
  inside pixel_scripts alone before today: in `PowerSupply`
  (core/power_supply.py), `DAQBase` (core/daq.py), and `FEB`
  (core/feb.py) - a genuine repeat-caller situation per the promotion
  rule in section 2, not a guess. `PowerSupply`, `DAQBase`, and `FEB` now
  all inherit `CommandMappable` instead of redefining these two methods.
  Fixed while unifying: 2 of the 3 original copies (DAQBase's and FEB's)
  had a copy-pasted error message referencing `self.equipment_name` - an
  attribute that only `PowerSupply` actually has. Would have raised
  `AttributeError` if that "command not recognized" branch had ever
  actually executed on a DAQBase or FEB instance. The shared version uses
  `type(self).__name__` instead, which always exists.
  Also standardized behavior: `PowerSupply`'s original `execute_command`
  always returned `True` regardless of the underlying command's actual
  result (and printed an extra debug line the other two didn't).
  `DAQBase`/`FEB`'s original versions returned the real result. Per
  explicit user decision, standardized on "return the real result" (the
  2-of-3 majority behavior) - this is a small behavior change to
  PowerSupply-derived instances specifically: any caller checking a
  truthy/falsy return from e.g. `power_supply.turn_on()` now sees the
  actual outcome instead of always True. Worth being aware of if
  anything downstream relied on the old always-True behavior (a search
  of pixel_scripts didn't find one, but this wasn't exhaustively traced
  through every caller).

3.5) common/status_message.py (new)
  `StatusMessage(odb_location)` - `send(result, msg="Nothing")` writes
  `<odb_location>/Result` and `<odb_location>/Message` to ODB, overriding
  the message to `"Success"` whenever `result`'s enum member is literally
  named `SUCCESS` (checked via `getattr(result, "name", None) ==
  "SUCCESS"`, so it works with any Enum-like type without common/ needing
  to import it - deliberately duck-typed instead of taking a
  success-sentinel parameter). `send_monitoring(msg)` writes only the
  Message field, for an in-progress update that shouldn't touch Result.
  Extracted from `ActionMessage` (actions/actions.py) and
  `CalibrationMessage` (calibrations/calibration.py), which were
  near-duplicates: same two ODB fields, same "Success" override logic,
  same debug print. Both classes are now thin subclasses that only supply
  their own `odb_location` default and (for ActionMessage/
  CalibrationMessage's own enum-typed default arguments) forward into
  `super().send(...)`. `CalibrationMessage.send_monitoring` needed no
  override at all - it's identical to the inherited one.
  Two dead instance attributes were dropped in the process
  (`self.action_result`, `self.message` as a plain string) - both were
  set in `__init__` and never read anywhere else in either repo
  (confirmed via `grep -rn "\.action_result\b"` /
  `grep -rn "message\.message\b"` across both repos before removing
  them).

6. VERIFICATION METHODOLOGY
----------------------------
Every changed/new file was checked with `python3 -m py_compile`
individually (syntax only). That was NOT enough on its own - it missed
core/power_partition.py's stale type hints pointing at classes that had
just moved out of core.power_supply (would have raised AttributeError
the first time anything actually imported that module, since Python
evaluates function-signature annotations eagerly at class-definition
time unless `from __future__ import annotations` is used, which this
codebase doesn't). Caught by building throwaway stub packages for `zmq`
(`from enum import Enum`) and `midas.client` (a no-op `MidasClient` with
stub `odb_get`/`odb_set`) - neither is installed in this shell - and then
actually importing every module in pixel_scripts and common_scripts with
both repo roots added to `sys.path` as siblings. All imports succeeded
after the power_partition.py fix. This is NOT proof that the real
PySequencer loader resolves `import common.odb` the same way - see the
open item in section 8 - but it does prove the code is internally
self-consistent under that assumption, which py_compile alone can't.

Separately, one real (not import-time) bug was found by reading actual
scifi-userfiles source and comparing byte-for-byte against what got
moved into common/power_supply.py:
`HVBoxNPowerSupply.turn_on`'s ODB path is
`.../Settings/Ouput On[ch]` (typo, missing the "t" - should be "Output")
while its own `turn_off` and `is_on` correctly use
`.../Settings/Output On[ch]`, and scifi-userfiles/scripts/hv_power.py's
real code confirms "Output On" is the correct key
(`/Equipment/HV/Settings/Output On[{ch}]`). As written, calling
`turn_on()` on an HVBoxNPowerSupply writes to a key that `is_on()` never
reads back from - the channel probably never actually turns on via this
code path. This is a PRE-EXISTING bug in pixel_scripts (not introduced
today), just carried along verbatim when the class was moved.
**Deliberately NOT fixed** - flagged for you to decide, since it affects
real hardware behavior and wasn't part of today's refactor scope.
One more, much more minor, unverified-but-probably-harmless observation:
DCDCPowerSupply writes to `.../Settings/Channel on[ch]` (lowercase "on")
while scifi-userfiles' lv_power.py uses `.../Settings/Channel On[ch]`
(capital). MIDAS ODB key lookups are believed to be case-insensitive, so
this is likely a non-issue, but it was not verified live against a real
ODB.


7. scifi_scripts STATUS (separate, currently on hold)
-------------------------------------------------------
Explicitly a hackathon experiment - replaces scifi-userfiles only if it
works out, not a committed migration. Decision made: mirror
pixel_scripts's top-level folder skeleton (actions/ calibrations/
config/ core/ globals/ scripts/ utils/) for architectural alignment, but
do NOT copy core/'s classes 1:1 - pixel's
Detector->PowerPartition->PowerSupply x3, FEB->Chip->DataLink hierarchy
encodes pixel's own hardware topology (ladder as power partition, MPDC+
DCDC+HVboxN triplet) which scifi doesn't have (scifi is
FEB->ASIC(mutrig)->fibre, no MPDC, no power-partition concept). Instead,
core/ should be designed around scifi's real topology using classes
named Feb/Asic/Channel (name chosen in the 2026-07-16 hackathon
brainstorm, HACKATHON.txt section 5.2), reusing pixel's PATTERN
(ODBCommand-based dispatch, prepare/execute/finalise, dependency-injected
MidasClient) rather than its literal classes.
As of this writing: only the 7 empty folders exist
(mkdir -p actions calibrations config core globals scripts utils inside
scifi_scripts/) - no files, no design started. User explicitly said to
leave this on hold and look at what's actually inside scifi-userfiles
first before continuing.
