2.5) A SEPARATE, REAL BUG found and fixed while reviewing comments

   repl. Practical effect: DCDCPowerSupply.turn_on() / read_current() /
   alert() did not exist as callable methods (map_commands_to_self()
   would create a method under the mangled name, not "turn_on") -
   AttributeError if ever actually called through the convenience
   method. Confirmed via `git log -p` that this bug predates today
   entirely (introduced in pixel_scripts commit 47375a1, "updated with
   actual ODB, added handling of control variables on power supplies" -
   just carried over verbatim into common/ during yesterday's
   promotion). Fixed by replacing the three malformed strings with real
   `#` comments. Verified fix locally (offline, stub client): commands
   dict now has the correct keys ("turn_on" etc), and calling
   dcdc.turn_on() / read_current() no longer raises.

3. NEW FILE: common_scripts/common/services.py (not yet wired to any caller)
---------------------------------------------------------------------
Implements the "Services" idea raised in this session, which turned
out to already be an explicit, unassigned ToDo in the 2026-07-16
"Operation Scripts" hackathon presentation (slide 19 - see section 6):
read-only pre-operation health checks for equipment shared across
power partitions (TDK power generators, DCDCCrates) - explicitly never
a turn-on/off surface, since a single TDK unit or DCDC crate feeds
multiple, unrelated power partitions.

  TDKService.check_status() -> (bool, str)
    OK if Fault Register == 0 and Interlock Trigger == 0 on every
    Enabled TDK channel (0/False = OK, same convention as
    DCDCPowerSupply's existing 'alert' readable). Verified live: all 6
    TDK channels currently OK (Fault Register / Interlock Trigger all
    zero). The 6 TDK channels are themselves confirmed genuinely shared
    across subdetectors (Names = 'SciFi & Tile US/DS', 'FE Crates
    US/DS', 'Pixel US/DS').

  DCDCCratesService.check_status() -> (bool, str)
    OK if every crate that is Enabled (configured/in use) is also
    Crate On (actually powered) - an enabled-but-unpowered crate would
    fail any calibration touching its channels. Verified live against
    real data: found ONE real, currently-true finding - crate
    "DCDC_C_3" (crate index 2) is Enabled but NOT Crate On. Not
    diagnosed further (could be intentionally off, e.g. detector not
    powered right now) - just confirms the check produces meaningful
    output, not a claim that this is a fault.

Standalone module, not yet imported/called from calibrationfactory.py
or anywhere else - left that way per explicit user instruction ("lascia
stare" / leave it standalone for now).

6. INCIDENT: stray MidasClient connections flooded mu3ebe's alarm log
---------------------------------------------------------------------
All live-ODB verification today (sections 2, 3) was done read-only via
SSH using ad-hoc `midas.client.MidasClient('gm_check')` connections,
several of which were not cleanly `.disconnect()`-ed at script exit.
This left a malformed `/Programs/gm_check` ODB record (wrong struct
size - a version/field mismatch between what the python client writes
and what the C++ alarm-checking code on mu3ebe expects), which MIDAS's
periodic alarm check (al_check) then repeatedly tried and failed to
repair, flooding the message log with struct-size-mismatch errors.

User fixed it directly on mu3ebe via `odbedit -c "deldir
/Programs/gm_check"`. User instruction: never do this again. Saved as
a standing feedback memory (feedback_midas_client_disconnect) - ad-hoc
MidasClient connections for quick reads must always disconnect cleanly
(try/finally or equivalent), not just exit after the last odb_get.
