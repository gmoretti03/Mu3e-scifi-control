PAGE I/O REFERENCE
====================================================================
NEW DOC 2026-07-24. Per-element input/output reference for the custom
control page ITSELF (distinct from scripts_io_reference.txt, which is
per-SCRIPT - NOTE added 2026-07-24 after a docs reorg: that file now
lives at docs/code/scripts_io_reference.txt, this one at docs/page/ -
every bare "scripts_io_reference.txt" mention below predates the move
and means that same file). This one is per-PAGE-ELEMENT: for every
field/button shown in custom_page_mockup_v2.html (custom_page_mockup_
colored.html's successor, archived to docs/old/ same day - see 2.2's
own note), where does the displayed value actually come from, and
where does an action on it actually go.

Built incrementally, one mega-section/zone at a time (user's own
approach, 2026-07-24) - sections not yet covered are marked PENDING.
Purpose: a single reference for whoever implements the real page,
cross-referencing scripts_io_reference.txt (the script-level params)
instead of duplicating it.

Legend - INPUT origin (where a displayed value comes from):
  ODB-LIVE    = read directly from a real ODB path, live state
  COMPUTED    = derived client-side from ODB-LIVE data already read
                elsewhere on the page - no separate ODB read
  PAGE-LOCAL  = exists only in the page's own JS state (selection,
                staged/unapplied edits - the PAGE tier from
                custom_page.txt 3.5) - never read from ODB
  HARDCODED   = a JS-side constant, not sourced from ODB at all

Legend - OUTPUT destination (where an action goes):
  ODB-DIRECT  = the page writes straight to an ODB path itself, no
                script/PySequencer involved
  PYSEQ       = the confirmed 3-write flow (State/Path+Filename,
                Param/Value/<name>, Command/"Start script") - triggers
                one of scripts_io_reference.txt's 5 entry points
  PAGE-LOCAL  = state that lives only in the page's own JS, never
                written to ODB by itself - selection (Power/Readout,
                every "Sel." checkbox) is the main use today. UPDATED
                2026-07-24: does NOT include a later separate HARDWARE-
                commit step for Power's Adjust/Demand or Readout's
                Mask/Enable anymore - those were simplified to single
                immediate actions this same day (2.2/2.3, 3.2) and no
                longer stage-then-apply. The 2-step stage/apply meaning
                of this term may still apply to Calibration (not yet
                covered here) - check the relevant section, don't
                assume from this legend alone.
  NOT-WIRED   = present in the mockup, no real behaviour yet (a true
                HARDWARE-tier placeholder - this still exists in
                Calibration's own Apply/Read/Stop buttons, not yet
                covered here; Power/Readout's own placeholders of this
                kind were removed 2026-07-24 along with the simplified
                actions above)
  NONE        = pure read-only display, no action attached

1.1) Emergency
  "Turn off all SciFi power" button
    INPUT:  none
    OUTPUT: PYSEQ - NO SCRIPT EXISTS YET. Needs a new aggregating
      script (e.g. scripts/all_power_off.py) that calls
      det.turn_off_all_feb_power() / det.turn_off_all_lv() /
      det.hv.turn_off() inside ONE sequence(), not 3 separate
      PySequencer launches - PySequencer is a single shared instance
      (custom_page.txt 3.1's concurrency note), so 3 sequential
      trigger-and-poll-Running round trips from the browser would be
      slow and fragile. CODE TODO, not built.
  "Turn off FEB" / "Turn off LV" / "Turn off HV" buttons
    INPUT:  none
    OUTPUT: PYSEQ -> feb_power.py / lv_power.py / hv_power.py,
      power_on=False (the only param this button needs to set;
      is_odb_available/can_send_commands_to_odb stay at script
      defaults). Verified in the scripts themselves (2026-07-24): the
      off path is unconditional and instant - no
      check_shared_equipment() gate, no settle_seconds wait, no
      post-action current check (on/off asymmetry is deliberate, see
      each script's own module docstring).

1.2) Required programs
  Program name list (mhttpd, SW Fibre, DCDC Frontend, HV Frontend,

      required_programs object (VTX_GenericDescriptions.js), itself
      hardcoded and setup-filtered, not read from ODB.
    OUTPUT: none

    INPUT:  ODB-LIVE - /Programs/<name>/First failed, formula x == 0
      (confirmed MIDAS-standard path+formula via
      VTX_GenericPrograms.js - pixel binds this through a "modbbox"
      custom element + configManager live polling, not a one-off
      fetch; reuse the same binding mechanism rather than reinventing
      polling).
    OUTPUT: NONE (display)

1.3) Service status
  DECIDED 2026-07-24: option 1 below, not option 2.
  TDK / DCDCCrates status dots
    INPUT:  ODB-LIVE (raw) + COMPUTED (client-side formula, ported 1:1
      from common_scripts/common/services.py):
      - TDK: reads /Equipment/TDK/Settings/{Names, Enabled,
        Fault Register, Interlock Trigger}; for every channel where
        Enabled is true, red if Fault Register != 0 or
        Interlock Trigger != 0 (mirrors TDKService.check_status()).
      - DCDCCrates: reads /Equipment/DCDCCrates/Settings/
        {Device Names, Enabled, Crate On}; red if Enabled is true but
        Crate On is false (mirrors DCDCCratesService.check_status()).
      Same pattern already used for "Required programs" above (raw ODB
      read + client-side formula) - not new infrastructure, just a
      small per-channel loop instead of a single scalar comparison.
      REJECTED option: a dedicated backend process that runs
      check_shared_equipment() periodically and publishes a single
      health flag to ODB - would remove the duplication below, but
      requires new always-on infrastructure (same category as the
      "no continuous safety interlock" gap already flagged in
      custom_page.txt 3.2, deliberately out of scope here too).
    OUTPUT: NONE (display), but mirrors the same interlock the
      Hardware-tier power-ON actions gate on (custom_page.txt 3.1) -
      disable/warn those buttons when red. This is UX only: the real
      enforcement stays server-side, each script still calls
      check_shared_equipment() itself at execution time regardless of
      what this card shows.
    KNOWN RISK, explicit for whoever implements this: the JS formula
      above and services.py's Python are two independent copies of the
      same logic - nothing keeps them in sync automatically. If
      TDKService/DCDCCratesService.check_status() ever changes, the JS
      copy must be updated by hand to match.

      INPUT: ODB-LIVE - FEBCrates/Variables/SCFC - shown as plain

    OUTPUT (all of the above): NONE (display)

  Selection: "Sel." checkbox column + select-all
    INPUT/OUTPUT: PAGE-LOCAL - lives only in JS state, no ODB write of

  Action: "Power on selected FEBs" / "Power off selected FEBs"
    INPUT:  selection (PAGE-LOCAL)
    OUTPUT: PYSEQ -> feb_power.py, params:
      power_on (True/False per button)
      target_febs - NEW param, does not exist in the script today
        (feb_power.py currently always loops over every Feb - CODE
        TODO). TYPE CONFIRMED 2026-07-24 (read midas/python/midas/
        sequencer.py's register_param()/get_param()): PySequencer
        params take their ODB type from register_param()'s
        default_value, so target_febs should be registered with a
        list default (e.g. []) -> MIDAS creates a native ODB INT
        ARRAY, not a JSON-encoded string. The page writes the selected
        feb_index values directly as an ODB array to
        /PySequencer/Param/Value/target_febs (same mechanism already
        used for every other array field on this page, e.g.
        FEBPower[]) - no JSON/CSV parsing needed on either side;
        feb_power.py just does target_febs = seq.get_param
        ("target_febs") and gets a plain list of ints back.
      is_odb_available / can_send_commands_to_odb: always True, never
        exposed as page controls (production page, not a dry-run tool)
    EMPTY-SELECTION BEHAVIOUR, DECIDED 2026-07-24 (user): clicking
      Run with nothing selected does NOT fall back to "every FEB" -
      nothing starts. (No script write happens at all in that case -
      implementer's choice whether that's a disabled button or a
      no-op with a message, not specified further.)
    FEEDBACK: after Command/"Start script", poll /PySequencer/State/
      {Running,Finished,Message,Error} and show the script's own

      check_shared_equipment() gate, which only applies to

      script.

      Running is true (single shared PySequencer instance).

2.2) LV power
  NOTE on interaction model, confirmed 2026-07-24 against the real
  mockup markup: the "Sel." checkbox and click-row-to-expand-detail are
  TWO INDEPENDENT interactions (the checkbox has an explicit
  stopPropagation() so clicking it never opens the detail panel).
  Selecting a row only ever builds the list for a batch action below -
  it does not change what data is displayed, expanded or not. Every
  value shown, in the main row or the detail panel, is ODB-LIVE either
  way - nothing on this table is computed from the selection state.
  Same note applies to FEB power (2.1) above.

  Main row columns (read-only, ODB-LIVE, no script involved):
    LV channel name (e.g. "SMB_US_2-3")
      INPUT: COMPUTED - derived from FEBName (ODB-LIVE) by parsing
        "<side> SM <n>" (detector/feb.py's __parse_name()/
        __build_lv_supply()); if FEBName doesn't parse, shown as a
        distinct "no LV supply assigned" row state, not blank/error
    present - ADDED 2026-07-24 (user request, prompted by the
      grouping-is-hardcoded discussion below: not a fix for that, but a
      cheap real-hardware sanity indicator worth having regardless)
      INPUT: ODB-LIVE - DCDCCrates/Settings/Present[ch] - confirmed
        real via the live ODB dump (docs/old/odb_220726_121718.json):
        128-element per-channel array, genuinely mixed True/False
        values (not a dead constant), with its own ODB-defined display
        format ("Format Present": [grey, var(--mgreen)]). NOT
        currently wrapped by DCDCPowerSupply's readables (common_
        scripts/common/power_supply.py) - a real, previously unused
        field, distinct from Enabled (configured) or on/off (powered):
        this is actual hardware-presence detection.
      OUTPUT: NONE (display) - a simple green/grey dot, no fault
        semantics (unlike the 7 detail-panel flags - Present isn't a
        pass/fail check, just "is there a physical channel here")
      CROSS-CHECKED against FEB/HV: FEB already has an equivalent real

        nothing to add there.
    active ch.
      INPUT: COMPUTED - same value as the FEB table's own active ch.
        column (a Feb's LV rail powers exactly its own channels)
    on/off
      INPUT: ODB-LIVE - DCDCCrates/Settings/"Channel on"[ch]
    Current
      INPUT: ODB-LIVE - DCDCCrates/Variables/Current[ch]
    Adjust (editable input, see action below - renamed from "Voltage":
      this IS the readback of the adjustable setpoint, not an
      independent measurement)
      INPUT: ODB-LIVE - DCDCCrates/Variables/"Voltage Adjust"[ch]
    ok/fault pill (aggregates the 7 flags below into one pass/fail)
      INPUT: COMPUTED - from the 7 detail-panel flags already read,
        no separate ODB read
    OUTPUT (all read-only fields above): NONE (display)

  Detail panel (click-to-expand, ODB-LIVE, independent of selection -

    Sense
      INPUT: ODB-LIVE - DCDCCrates/Variables/"Vdd MuPix"[ch]
    Temperature
      INPUT: ODB-LIVE - DCDCCrates/Variables/Temperature[ch]
    7 fault flags (Alert, Power Good, Over Temperature,
    Vin Under-voltage, Over Current, Vout Over-voltage, Interlock) -
    real hardware flags, safe to color-code red/green directly (unlike
    the raw Current/Adjust/Sense/Temperature numbers above)
      INPUT: ODB-LIVE - DCDCCrates/Variables/<flag name>[ch] (Power

  Action: "Adjust" - RE-CORRECTED 2026-07-24, SIMPLIFIED (the 2-step
  PAGE-then-HARDWARE model written earlier the same day is now
  SUPERSEDED - kept out of this doc entirely, not left as a "kept for
  the trail" note, since it was live for less than an hour and never
  reached the real page). Reasoning for reverting: the stage/apply
  split earns its complexity in Readout (a big multi-way selection
  across a 512-channel grid, built up over several clicks before
  committing) and Calibration (a full multi-parameter scan config,
  staged before an expensive, slow, real hardware action). Adjust is
  neither - it's one number, one write, with NO server-side validation
  to protect on either side of a stage/apply split (see below) - so
  staging bought nothing and introduced a real ambiguity (a staged
  edit and the last-polled live value would occupy the exact same
  field in a real implementation, with no way to tell them apart, and
  a live ODB poll could silently clobber an unsaved edit). Reverted to
  a SINGLE action, same shape as the FEB/LV/HV power actions above:
    Per-row Adjust input, or the bulk field + ONE button ("Set adjust
    for selected")
      INPUT:  selection (PAGE-LOCAL) + typed value
      OUTPUT: ODB-DIRECT (OPTION A, unchanged) -
        DCDCCrates/Variables/"Voltage Adjust"[ch], written immediately

      scripts/common/power_supply.py's DCDCPowerSupply.set_voltage()
      writes Settings/Adjust[ch] (a 40-element array) instead of the
      real, hardware-watched Variables/"Voltage Adjust"[ch] (128
      elements) - confirmed against the dcdc_fe frontend source
      (mdev_pdcc.cxx). Out of bounds for every one of SciFi's channels
      (indices 6-121). MUST be fixed in common_scripts (shared with
      pixel_scripts, not SciFi-specific) before this action can work at
      all. The Option-A direct write from the page bypasses
      DCDCPowerSupply's own (buggy) command entirely, so fixing the
      page's own write path doesn't require touching the Python class
      - but the class should still be fixed too, since other callers
      may use it.
    NO VALIDATION ANYWHERE, explicit user decision (kept from an
      earlier session, re-confirmed here): unlike HV's Demand (which
      mdev_hv4.cxx clamps at the firmware level), DCDCCrates' own
      frontend has no equivalent bounds check on Voltage Adjust writes
      - the page adds no client-side clamp either. The old -9..+21V/
      step 1.5 bounds from DCDCPowerSupply's class attributes exist in
      Python but are NOT enforced anywhere on this write path.
    "Turn on selected" / "Turn off selected": unrelated, separate
      action - this is the main LV power action already documented
      above (power_on/target_febs/settle_seconds/... via lv_power.py),

      behaviour for today's bulk-only script (not a bug), but a real
      trap for an operator who doesn't know it: setting 3 different

4.4) PER-MODULE PARAMETERS - THE SCAN LOOP ITSELF, DESIGNED 2026-07-24
  for ScanVbr/IV scan specifically (Thr scan's own equivalent is a
  DIFFERENT, not-yet-designed problem - see note at the end). Today's
  ScanVbr sweeps every channel together on ONE shared voltage axis (one
  Demand value, written to every channel, per step) - per-module
  iv_start/iv_end/iv_step breaks this, since different channels would
  need different voltage sequences with different step counts. Proposed
  design, NOT YET BUILT (revisit when this becomes real code work, not
  before):
    1. PRECOMPUTE, once at prepare(): for every targeted HV channel,
       build its own voltage sequence from that channel's own
       iv_start/iv_end/iv_step (read from the per-module dict, 4.3) -
       no longer one shared sequence for everyone.
    2. PAD to a common length: the shortest sequences are extended by
       holding their own final value, so every channel has the same
       total tick count (the max across all targeted channels) - lets
       the scan still use ONE shared tick loop instead of N independent
       ones running at different paces.
    3. PER-TICK WRITE: at each tick, write each channel's OWN value for
       that tick - requires extending ScifiHv.set_demand_channels()

    4. SETTLE TIME: if settle_seconds differs per module, use the MAX
       settle_seconds among the channels still actively stepping at
       that tick (never wait less than any channel individually needs)
       - accepts some wasted wait time on faster-settling channels
       rather than under-waiting any of them.
    5. current_limit_ua / fit_window_v / min_peak_prominence /
       run_vbr_finding: already evaluated PER-CHANNEL in the existing

       problem above, mostly a lookup-source swap.
