====================================================================
HOW A CALIBRATION ACTUALLY GETS STARTED - CONFIRMED MECHANISM
====================================================================
Verified against the real ODB dump's /PySequencer tree AND the real
midas/python/midas/sequencer.py source (both local, no mu3ebe read
needed or done):
  /PySequencer/State/Path + Filename   - which script is loaded
  /PySequencer/Command/Load new file   - loads it (True/False)
  /PySequencer/Command/Start script    - starts it (True/False)
  /PySequencer/Param/Value/<name>      - PySequencer's OWN generic
                                          params - confirmed these only
                                          hold execution-mode flags
                                          (is_odb_available, etc.), NOT
                                          calibration selection/settings
Confirmed real (not just ODB-dump-shaped, but actually consumed) via
sequencer.py:1597/1607 - `if odb_commands["Start script"]:` / `if
odb_commands["Load new file"]:` are real polled conditions in the
engine loop.

CONCLUSION: the page does NOT need to touch PySequencer's generic
param mechanism at all for calibration selection/settings - it mirrors
pixel's own existing pattern (get_calibration_to_perform_from_odb())
of reading a dedicated ODB tree instead. The page only needs to set
Start script = True (Load new file only if the generic launcher script
isn't already the one loaded - expected to be the steady state, not
something the page needs to manage every time).

====================================================================
PAGE SECTION - FOUR PIECES, AGREED SCOPE FOR THIS FIRST PASS
====================================================================
1. Calibration selector (ScanThr / ScanVbr) - writes CurrentCalibration.
2. Parameter form, one per calibration - the fields listed above,
   editable directly on the page.
3. "Start Calibration" button - writes the selected calibration's
   parameters to its ODB folder, then /PySequencer/Command/Start
   script = True.
4. A readiness badge before the button, mirroring the same shared-
   equipment gate already built and verified in common/ this week
   (TDK/PowerDist/DCDCCrates/required programs/alarms) - so the
   operator sees red/green BEFORE pressing Start, not after it fails
   server-side. Same "traffic light" convention already used
   throughout every other tab of this page.

DELIBERATELY DEFERRED, not part of this first pass: live progress
feedback while a calibration is running (which step, how far along).
Requires the calibration SCRIPT itself to write progress somewhere
pollable in ODB - a two-sided change (script + page), not page-only.
Decided to ship selector+form+button+readiness-badge first (useful and
independently verifiable with no script-side changes needed), add
progress as a second pass once that's working.

IV SCAN (ScanVbr) - NEW SCRIPT CHECK LIST, AGREED 2026-08-07
====================================================================
The current vbr_scan.py is being rewritten from scratch. Before writing
it, agreed the full check list it must run - and confirmed with the
user the scope rule for ALL of them: every check applies ONLY to the
selected modules the scan will actually run on, never whole-detector
(supersedes the old script's whole-detector LV gate, which was only
that broad because the channel<->module mapping wasn't known at the
time - it's known now, via HV_BOARDS).

PRE-FLIGHT (block Start if any fails, scoped to selected modules only):
1. Parameters valid: 0 <= iv_start <= iv_end <= 60V (MAX_DEMAND_VOLTAGE),
   iv_step >= 1. Pure validation, no hardware state needed.
2. Every selected module has a mapped HV channel (already enforced on
   the page - unmapped modules can't be checked/selected).
3. HV Output On set on the selected modules' channels.
4. LV Power Good on the selected modules' Febs.
5. Feb connected/powered for the selected modules.
6. Shared equipment (TDK/PowerDist) healthy for the side/zone of the
   selected modules.
7. Required Programs alive (HV Frontend, DCDC Frontend, Febcrate
   Frontend).
8. No active alarm relevant to the selected modules.

RUNTIME (during the sweep, selected channels only, not pre-showable):
9. Over-current per channel (Current > Settings/"Current limit") - cut
   that channel's Demand to 0, keep sweeping the rest. Same behaviour
   as the old script's __check_over_current().

POST (always runs, success or failure):
10. Hardware cleanup (readout config reset).

PAGE STATUS vs this list, as of today: checks 3 (HV dot), 4 (LV dot),
5 (FEB dot) already have their live status shown per-module row in the
IV table (2026-08-07 dot columns). NOT yet shown/enforced anywhere on
the page: 1 (param validation), 6 (shared equipment), 7 (only 3 of the
Programs are surfaced, in the message row, not gating), 8 (alarms) -
and none of 1/3/4/5/6/7/8 currently BLOCK Start, they're informational
only.

BLOCK vs INFORMATIONAL DECISION, agreed 2026-08-07:
  BLOCKS Start (deterministic/confirmed-critical, scoped to selected
  modules only):
    1. Parameter validation - pure client-side, no ambiguity.
    3. HV Output On - script assumes it's already set, doesn't turn it
       on itself; running with it off produces meaningless data.
    4. LV Power Good - confirmed real safety gate in the actual old
       prepare() (don't bias SiPMs near unready readout electronics).
    6. Shared equipment (TDK/PowerDist) for the selected modules' zone
       - PowerDist feeds the HV crate itself (see hvPowerDistHealth()
       in SciFi_PowerHV.js) - same criticality as Programs being down.
    7. Required Programs alive.
  INFORMATIONAL ONLY (dot/message, does not block Start):
    8. Alarms - too broad/noisy to hard-block on automatically; shown,
       left to operator judgement unless a reliable per-module alarm
       filter is found later.
  Check 2 (module has a mapped HV channel) is already structurally
  enforced - unmapped modules' checkboxes are disabled, can't even be
  selected.

  CHECK 5 REMOVED ENTIRELY, 2026-08-07 (user asked, confirmed by
  re-reading the code): the Feb datapath/link/crate chain has NO
  bearing on an IV scan at all - the measurement is HV Current/Voltage
  read directly from the HV supply, never touches the Feb's digital
  readout. Cross-checked against pixel: IVScan.prepare() ->
  check_all_pp_on() -> PowerGroup.is_on() only checks PowerDistribution
  + LV + HV, never chip/readout state either - no precedent there for
  a Feb-equivalent check on an IV-style scan. Removed the FEB dot
  column from the IV table entirely (kept on Thr scan's table, where
  the datapath genuinely matters - it reads ASIC channel data) and
  dropped Febcrate Frontend from item 7's Program list for IV scan
  specifically (item 7 for IV scan is now just HV Frontend + DCDC
  Frontend).

FINAL BLOCKING SET for IV scan: 1 (params), 3 (HV Output On), 4 (LV
Power Good), 6 (shared equipment), 7 (HV Frontend + DCDC Frontend
Programs only, no Febcrate Frontend). INFORMATIONAL: 8 (alarms).

PAGE <-> ODB RESULTS - IMPLEMENTATION LIST, 2026-08-07

Today the page only WRITES to ODB (params + selected_channels) and
fires Start - nothing reads back the ScanVbr/<module>/ results
structure calibration_process.txt now defines. Full list of what's
needed, in no particular priority order yet - to be picked up one at a
time:

1. STATUS DISPLAY - DONE, 2026-08-07. IV table now fetches the whole
   ScanVbr subtree in updateCalibrationTab() (one extra
   mjsonrpc_db_get_values path, CAL_ODB_DEFAULTS_BASE + "/ScanVbr" -
   directory fetch, confirmed live against the real running mhttpd RPC
   endpoint that this returns a nested object with LOWER-CASE keys,
   e.g. data.us_sm0_m0.status), looked up per row via
   (side+"_SM"+sm+"_M"+realModule).toLowerCase(), shown as a pill
   (statusPill + new CAL_STATUS_PILL_STATE map) next to the HV/LV dots.

2. "NEVER RUN" STATE - DONE, 2026-08-07, same change as #1. A row with
   no ivResult (module has no ScanVbr/<module>/ entry, or the whole

   autoUpdater/source pattern from Scifi-monitor.js (that's built for

   IV table rows became click-to-expand (row-clickable + chevron, same

   2s tick (same as the rest of this page - no persistent-instance

   subscription. Also folded in the user's follow-up ask ("qui dentro
   si potrebbero inserire le info sulla calibrazione che salviamo in
   odb no?") - the same detail panel shows HVChannel/Status/Message,
   ParametersUsed (the real params the saved result was run with, not
