THE UNIVERSAL CALIBRATION PROCESS
====================================================================
Written 2026-08-06. Reference definition of the calibration process,
grounded in pixel_scripts' real, working, verified implementation -
the same shape scifi_scripts will be migrated onto once common/ is
judged complete. Lists, for every step, which common_scripts/ file
implements it, its verification status, and what stays subsystem-
specific by design (never moves into common).

====================================================================
THE 8 STEPS
====================================================================

1. ENTRY POINT
   Subsystem-specific glue - the PySequencer script (pixel_scripts/
   scripts/run_calibration.py) receives `seq` (already a real
   MidasClient, confirmed via midas/python/midas/sequencer.py source -
   no separate client needed). Not common - this is where subsystem
   and PySequencer meet.

2. SHARED-EQUIPMENT GATE
   Read-only pre-operation health check on equipment shared ACROSS
   power partitions/FEBs - must pass before anything else runs.
   COMMON: common/equipment/services.py
     - TDKService, PowerDistService, DCDCCratesService, ProgramService,
       AlarmsService
     - check_shared_equipment() / check_shared_equipment_or_print() -
       aggregates all five, stops at first failure
     - name_filter (substring) + channel_indices/device_indices
       (explicit index list) let a subsystem declare its own curated
       equipment dependency list; program_names/alarm_names do the same
       for ProgramService/AlarmsService - every list stays in the
       subsystem's own code, mirroring how the real SciFi custom page
       keeps PD_HV/PD_WEATHER/PD_FEC/PD_CRATE_MAINS/PD_SMB_LDO and its
       own required-programs/alarm-names arrays hardcoded in its own
       JS, not in a shared file.
   STATUS: mechanism DONE and verified field-by-field against the real
   ODB dump and the real page's own JS for all five services (including
   the Fault-Register/First-failed/LinkStatus hex-string/WORD-type
   verification against midas.client's own source, and the Alarms
   Triggered field's plain-INT32 verification).
   PIXEL NOW WIRED (2026-08-06): actionfactory.py/calibrationfactory.py
   pass name_filter="Pixel" + pixel's own evidence-based required_
   programs (mhttpd/Sequencer/DCDC/HV/Powerrack Frontend) and required_
   alarms (the 8 "FEB Crate N Temperature" alarms) - both live in
   pixel_scripts/globals/setup.py, deliberately excluding items with no
   direct evidence of applying to pixel (Febcrate Frontend/SW Fibre,
   SciFi-only cooling alarms).
   OPEN: SciFi's own real curated lists (TDK channel_indices, PowerDist
   device_indices, program_names, alarm_names - all now KNOWN from the
   page's own JS) are still unwired - deferred to SciFi's own
   migration.

3. TOPOLOGY / DETECTOR CONSTRUCTION
   Build the objects representing this subsystem's controllable power
   hardware.
   COMMON (the building blocks, not the assembly):
     - common/power/supply.py - PowerSupply hierarchy (LVPowerSupply/
       HVPowerSupply/DCDCPowerSupply/MPDCPowerSupply/HVBoxNPowerSupply)
       + PowerSupplyFactory
     - common/power/group.py - PowerGroup (LV+HV+PowerDist slots,
       is_on/turn_on/turn_off, read_all_readables/check_selected_health)
     - common/power/feb_crate.py - FebCratePower(client, link_feb) -
       NEW today, turn_on()/turn_off()/get_power_monitoring() for one
       FEB's crate-slot power, extracted+generalised from scifi_
       scripts/detector/feb.py's own (already working) implementation
   NOT COMMON, by design: HOW a subsystem assembles these bricks into
   its own topology. Confirmed today that pixel and scifi do this
   DIFFERENTLY - pixel groups multiple channels into PowerPartition
   (extends PowerGroup); scifi has NO partition concept at all, works
   flat per-FEB (each Feb owns its own LV supply directly, HV is one
   flat/global object, not per-Feb). Each subsystem's own Detector
   class stays subsystem-specific.
   STATUS: PowerSupply/PowerGroup DONE+verified (pixel uses them
   directly). FebCratePower + check_link_status DONE+verified AND NOW
   WIRED INTO PIXEL (2026-08-06): core/feb.py's FEB gained get_
   link_feb() (read from ODB, distinct from get_number()); actions/
   febactions.py's ActionFebPowerOn/Off call bringup_declaration.
   build_feb_sequence(feb) for every FEB. Verified end-to-end against
   REAL dump data (not just dry-run): a real FEB's full bring_up() run
   correctly wrote FEBPower and verified both crate power and link
   status. SciFi's own Feb class not touched (deferred to its own
   migration) - but the same common/ code is ready for it.

4. DETERMINE WHAT TO RUN
   Read the calibration-to-perform enum value from ODB, dispatch to
   the concrete calibration class.
   Subsystem-specific: the enum itself (pixel: CalibrationExecute /
   IV_SCAN, SMOKE_TEST; scifi: CalibrationExecute / SCAN_THR, SCAN_VBR)
   and its ODB path (/CosmicRun/Calibration/<Subdetector>/
   CurrentCalibration - same tree shape confirmed for both).
   COMMON: common/odb/commands.py's read_odb_value_or_default() is the
   reusable dry-run/missing-path-fallback shape behind this kind of
   read, already used elsewhere.

5. BRING-UP
   Get the relevant power hardware from off to on-and-stable, one
   step at a time, each step's precondition checked before writing.
   COMMON: common/power/bringup.py - StepKind enum, Step, BringUpSequence
   (bring_up()/power_down(), stops at first failed step, power_down()
   runs the list reversed).
   Subsystem-specific: the actual declaration (which steps, in what
   order, with what preconditions/actions/verifications).
   STATUS: engine DONE+verified - including a real fix found while
   building the FEB declaration below (VERIFY_VALUE/VERIFY_PROGRAM
   steps now correctly poll/wait instead of checking once with no
   retry). Pixel's own LV+HV declaration DONE+verified (pixel_scripts/
   actions/bringup_declaration.py - 4 steps). FEB bring-up DONE AND
   WIRED (2026-08-06) - common/power/feb_crate.py's build_feb_bringup_
   sequence() (2 steps: feb_crate_power_on, link_status_ok), genuinely
   generic, lives in common/ itself, serves both pixel and scifi with
   the SAME declaration. Pixel now calls it for real via actions/
   febactions.py's ActionFebPowerOn/Off (wired into ActionFactory,
   dispatched via ActionExecute.FEB_POWER_ON/FEB_POWER_OFF). SciFi's
   OWN LV/HV declarations (documented in docs/old/chain_and_
   monitoring.txt section 14) still NOT built as BringUpSequence code -
   FEB is the only bring-up piece ready to reuse as-is for SciFi too.

6. CALIBRATION LIFECYCLE
   prepare() -> execute() -> finalise() (ALWAYS, regardless of
   execute()'s outcome), each step's result appended, driven by one
   run() that owns opening/closing the result saver.
   COMMON: common/operation/base.py (OperationBase), action_base.py
   (ActionBase), calibration_base.py (CalibrationBase), result.py
   (OperationResult enum), status_message.py (StatusMessage).
   STATUS: DONE+verified for pixel, including the multiple-inheritance
   split (pixel's own core/operation_base.py mixin for append_step_
   result_and_check + common's generic orchestration). SciFi's own
   calibrations/calib_base.py's CalibrationBase does NOT extend
   common's yet - it still inlines its own prepare/execute/finalise
   orchestration in calib_run.py (already has the "always finalise"
   fix by hand, matching common's logic in spirit, but not literally
   sharing the code) - migration deferred to SciFi's own pass.

7. RESULT SAVING
   Record initial status, append each step's result, ALWAYS save a
   final result (same guarantee as step 6's finalise()).
   COMMON: common/results/saver.py (ResultSaver family - Local/ODB/
   RunDB/Multiple), common/results/interpretation.py (get_last_
   measurement, compare_read_outputs, etc.).
   STATUS, per class (corrected 2026-08-07 - the previous "DONE+verified"
   note here was wrong, it only ever applied to ResultSaverLocal):
     - ResultSaverLocal: DONE, real (ndjson file, get_last_execution_
       number rotation).
     - ResultSaverODB: was an empty __init__-only stub until today.
       IMPLEMENTED 2026-08-07 (user: "dobbiamo assolutamente sistemare
       la cartella results in common") - generic, calibration-agnostic:
       append_step_result(result) grows one ODB array per dict key
       under odb_folder+"/Output/"; save_final(result) writes each key
       flat (not arrays) under odb_folder; Status set to "Running"/
       "Done" automatically. Deliberately treats ODB as the CURRENT/
       LATEST state only (overwrites, no versioning - see the ODB vs
       CDB section further down), matching what this whole file's IV-
       scan ODB structure design needed. Uses the existing setup.
       is_odb_available/odb.read_odb_value_or_default dry-run
       convention, same as every other class in common/. ResultSaver
       Multiple gained a client= param to pass through. Verified:
       py_compile, a dry-run smoke test (record_initial_status/3x
       append_step_result/save_final/save_final(None)), AND the full
       pixel test1-5.py suite (PYTHONPATH=common_scripts:. needed to
       run them directly) - zero regressions, all 5 still pass.
     - ResultSaverRunDB: still an empty __init__-only stub - the CDB/
       RunDB historical-record counterpart, explicitly NOT done today,
       separate follow-up.
   Nothing in pixel_scripts actually INSTANTIATES ResultSaverODB/
   ResultSaverMultiple yet (confirmed by grep - only test5.py touches
   ResultSaverLocal directly) - the class now works correctly but has
   no real caller wiring it into a live calibration's prepare/execute/
   finalise flow, for pixel OR SciFi. SciFi still has ZERO result
   saving today - deferred to SciFi's own migration, unchanged.

   common/results/interpretation.py CLEANED UP 2026-08-07 (user: "sì
   lavoriamo su interpreter"): get_last_lv_current/get_last_lvds_
   error_rates were pixel-specific (hardcoded "Power"/"LV"/"LVDS" keys
   matching core/operation_base.py's own step_result shape, and pixel-
   only chip.data_links/get_positional_id()/get_position_in_chip()
   vocabulary) sitting in common/ despite not being usable by any other
   subsystem - moved to NEW pixel_scripts/calibrations/interpretation.py.
   Found real, confirmed evidence they were never actually being called:
   calibrations/smoketest.py duplicates the exact same dict-drilling
   manually inline instead (4x, with its own "this is getting
   cumbersome..." comment) - a real cleanup opportunity for later, not
   done today (out of scope for "lavoriamo su interpreter", would mean
   editing pixel_scripts's already-verified calibration logic).

   FURTHER PASS same day (user: "aggiungi altre cose che possono esser
   universali"): re-examined get_last_measurement itself - it ALSO
   turned out to be pixel-shaped, not universal (unwraps step_results
   assuming pixel's own single-key-per-step {step_name: {...}} wrapper
   convention from append_step_result_and_check() - confirmed by grep,
   its only callers were the two functions just moved out). Moved it to
   pixel_scripts/calibrations/interpretation.py too, alongside the
   functions that actually use it.

   common/results/interpretation.py FINAL contents, all genuinely shape-
   agnostic (no assumption about what a calibration puts in
   step_results): compare_read_outputs (pre-existing, power_supply/
   variable names are caller-supplied), get_step_count, get_step_result
   (index), get_field_series (field_name) - the last one directly useful
   for the flat per-step shape this file's own IV-scan design uses
   (e.g. {"Voltage": v, "Current": i}), extracting a full series across
   every step without ODB. Verified: py_compile all files, full pixel
   test1-5.py suite (zero regressions), and a direct exercise of the 3
   new functions against a flat SciFi-shaped fake result_saver
   (get_field_series correctly returned [54.0, 54.2] for "Voltage" etc).

   THIRD PASS same day (user: "sicuro che questi due file siano a
   posto? c'e' da aggiungere altro?" - re-examined the REAL caller,
   common/operation/base.py's OperationBase.run(), instead of trusting
   the earlier design/tests alone). Found and fixed 2 real bugs:
     a. OperationBase.__init__ built ResultSaverMultiple WITHOUT ever
        passing client= - has_odb_result is hardcoded False today so
        this never actually crashed, but was a live landmine: the day
        has_odb_result flips True, ResultSaverODB would get client=None
        and crash on its first real odb_set(). Fixed: now passes
        client=det.client (Detector always has this attribute, real
        client or None in no-odb mode - confirmed in core/detector.py).
     b. save_final(result) in the REAL flow is called with the bare
        operation_result.OperationResult enum member (SUCCESS/FAIL/
        etc.), never a dict - confirmed by reading OperationBase.run()'s
        actual finally block. The original implementation unconditionally
        wrote Status="Done" regardless of what actually happened - a
        POWER_FAIL run would have been indistinguishable from a real
        success in ODB. Fixed: Status now reflects the real
        OperationResult.value ("Success"/"Power Fail"/etc.) when an Enum
        is passed; the dict-handling branch (Status="Done" + flat
        fields) stays as a secondary path for a calibration choosing to
        call save_final itself with extra data, but the enum path is
        what actually fires today.
     c. (found in the same pass) append_step_result was reading the
        CURRENT ODB array back via read_odb_value_or_default and
        appending to IT, not to the in-memory step_results. This meant
        a NEW calibration run (fresh ResultSaverODB instance) on the
        SAME channel would silently inherit and keep growing the
        PREVIOUS run's leftover array forever - directly violating this
        file's own "ODB is current-state-only, never a history" rule
        agreed earlier today. Fixed: now rebuilds the full array from
        self.step_results (already reset fresh per instance in
        __init__) on every call - no ODB read-back needed at all,
        and a fresh instance can never inherit stale data.
     d. Added _normalize() (Enum -> .value, everything else passthrough)
        used in both append_step_result and save_final's dict branch -
        the real {"Final_Result": final_result} step OperationBase.run()
        appends contains a raw OperationResult enum member, which isn't
        directly ODB-serializable; confirmed via a direct test it now
        writes "Success" (str) instead of the raw enum object.
   Verified all 4 fixes: py_compile (saver.py + operation/base.py),
   direct tests reproducing the exact real call shapes (Enum passed to
   save_final, Enum-in-dict passed to append_step_result, two separate
   instances against the same odb_folder proving no cross-run
   contamination), and the full pixel test1-5.py suite again - zero
   regressions throughout.

   FOURTH PASS same day (user: "controlliamo anche interpretation.py
   con lo stesso approccio e aggiungi se pensi sia utile e universale").
   Re-verified compare_read_outputs against its REAL caller chain
   (actions/daqactions.py's ActionResetBiasBlock -> evaluate_current_
   jump -> detector.read_all_power() -> power_group.read_all_readables()
   - the {pp_name: {power_supply: {variable: value}}} shape it assumes
   matches exactly) - no bug found, genuinely correct and generic
   already. Added get_odb_value(client, odb_folder, field_path,
   default=None) - the missing READ counterpart to what ResultSaverODB
   WRITES (Output/<field>, Status): nothing could read that structure
   back outside a live result_saver's in-memory step_results before
   this. Deliberately a single generic primitive (caller supplies the
   full field_path, e.g. "Output/Voltage" or "Status") rather than
   hardcoding the "Output/" prefix into two separate wrapper functions -
   stays agnostic about the folder's internal layout. Considered adding
   more (e.g. listing all field names ever seen across steps) but
   deliberately stopped - no concrete need behind it, unlike the other
   additions which each trace to something real that already needed
   them. Verified: py_compile, a dry-run read against the exact paths
   ResultSaverODB writes (Output/Voltage, Status), full pixel test1-5.py
   suite - zero regressions.

8. RETURN / REPORT
   Subsystem-specific glue back to the PySequencer (seq.msg(), print,
   etc.) - not common. NOTE (found 2026-08-06): everything returned/
   printed by common/ so far (ProgramService etc.) is page-banner-style

   not cm_msg). Whether real calibration failures should become actual

   question for later, not decided or built here.

SCIFI IV SCAN (ScanVbr) - CONCRETE CHECK VALUES FOR THE NEW SCRIPT
====================================================================
Written 2026-08-07. Resolves this file's own step-2 "OPEN" item above,
for IV scan specifically - real values, not placeholders, all taken
from the real ODB dump / the real page's JS (SciFi_PowerHV.js,
SciFi_Geometry.js, SciFi_Calibration.js) while building the page's own
warning checks today. The new vbr_scan.py (still to be written from
scratch) should reuse these, not rediscover them. Per the philosophy
agreed today ("i veri gate bloccanti saranno nei .py"), THESE checks
are the real enforcement - the page's own copy is informational only.
ALL of them are scoped to the modules actually selected for the scan,
never whole-detector (agreed explicitly with the user).

1. PARAMETERS (pure validation, no ODB read):
   0 <= iv_start <= iv_end <= hv.ScifiHv.MAX_DEMAND_VOLTAGE (60.0)
   iv_step >= 1

2. PER SELECTED MODULE - HV channel:
   HV_BOARDS mapping (side + real module number 0-11 -> HV channel
   index in /Equipment/HV/Settings/Names, currently ONLY defined in
   SciFi_PowerHV.js - needs porting into hv.py, doesn't exist there
   today):
     US Top:    namesBase=20,  modules=[null,null,2,3,4,5,6,7]
     US Bottom: namesBase=72,  modules=[null,null,8,9,10,11,0,1]
     DS Top:    namesBase=132, modules=[null,null,2,3,4,5,6,7]
     DS Bottom: namesBase=188, modules=[10,11,0,1,null,null,8,9]
   (channel index = namesBase + position-in-modules-array; a null
   entry means that module has no HV channel at all - refuse
   selecting it, same as the page does today.)
   Check: Settings/Enabled[idx] AND Settings/"Output On"[idx] both
   true (script assumes HV is already on, never turns it on itself).

3. PER SELECTED MODULE - LV/DCDC channel:
   Resolution already exists in Python: Feb.has_lv_supply() / Feb.
   check_lv_power_good() (detector/feb.py) - reuse these directly, no
   new mapping needed on the LV side.
   Check: Present + Channel On + no fault flags (Alert/Power Good/Over
   Temperature/Vin Under-voltage/Over Current/Vout Over-voltage/
   Interlock) - matches check_lv_power_good()'s existing logic.

4. PER SELECTED MODULE - DCDCCrates CRATE-level (NEW - not covered by
   check_lv_power_good(), which is channel-only):
   /Equipment/DCDCCrates/Settings/Enabled[crateIndex] AND
   /Equipment/DCDCCrates/Settings/"Crate On"[crateIndex], where
   crateIndex = floor(channelIndex / ChannelsPerDevice). Dedup per
   crate - several selected modules can share one.

5. SHARED EQUIPMENT - PowerDist, per HV zone (US Top/US Bottom/DS Top/
   DS Bottom) touched by the selected modules:
     PD_HV      = [102, 103, 118, 119]   (US Top, US Bottom, DS Top, DS Bottom)
     PD_WEATHER = [100, 101, 116, 117]   (same order)
   device = floor(PD_HV[zone] / ChannelsPerDevice) (= floor(idx/32))
   Check, in order (stop at first failure, matches hvPowerDistHealth()
   in SciFi_PowerHV.js):
     a. Settings/Enabled[device] true
     b. Settings/"Device on"[device] true
     c. Settings/"Output On"[ch] AND Settings/"Power good"[ch] true,
        for both PD_HV[zone] and PD_WEATHER[zone]

6. SHARED EQUIPMENT - TDK mains, per side (US/DS) touched by the
   selected modules:
   /Equipment/TDKStaging/Settings/Names - match "SciFi & Tile <side>"
   (NOT "FE Crates <side>", which is a different channel serving LV/
   FEB crates only - confirmed indices in the real dump: [0]="SciFi &
   Tile US", [1]="SciFi & Tile DS", [2]="FE Crates US", [3]="FE Crates
   DS", [4]="Pixel US", [5]="Pixel DS", but match by NAME not index,
   TDK's channel count/order isn't guaranteed stable).
   Check (only if Settings/Enabled[i] true for that channel):
     Settings/"Fault Register"[i] == 0 (WORD/hex-string - decode same
       as TDKService already does)
     Settings/"Interlock Trigger"[i] == False
     Settings/"Output On"[i] == True

7. RUNTIME (during the sweep, not a pre-check) - per-channel over-
   current: if Variables/Current[idx] exceeds Settings/"Current
   limit"[idx] (or reads NaN), cut that channel's Demand to 0 for the
   rest of the sweep, keep sweeping the others. Same behaviour as the
   old vbr_scan.py's __check_over_current() - keep it as-is.

NOT COVERED here, deliberately (per the 2026-08-07 decision to drop
it): Feb datapath/link/crate-power state (PLL/RX/DPA lock, FEBPower,
CrateControllerConnected) - confirmed not physically relevant to an HV-
only measurement, see this file's step-2 discussion and calibration_
page_plan.txt's "FEB CHECK REMOVED ENTIRELY" entry for the reasoning.
Programs and Alarms are checked by common/equipment/services.py's
existing ProgramService/AlarmsService (step 2, generic mechanism) -
this section only lists what's SPECIFIC to IV scan beyond that.

SCIFI IV SCAN (ScanVbr) - ODB RESULTS STRUCTURE, AGREED 2026-08-07
====================================================================
Resolves step 6's RESULTS STRATEGY "ODB: some monitoring-facing ODB
folder... someone can explain how" line - found the real precedent
instead of guessing. Checked the current live ODB dump (Docs/
devolpment/odb_070826_134730.json, 2026-08-07 - the scifi_scripts/
docs/ dump this was originally tracked in no longer exists, see
[[feedback_odb_dump_reference]]) for /CosmicRun/Calibration/VTX/ and
found it's NOT just the bare CurrentCalibration selector
calibrationfactory.py suggested - there's a real, actively-written
sibling folder: VDAC_power_consumption/, per power partition (e.g.
"VTX_US_L1_M1"), shaped:
  Parameters/       - the sweep's bounds (VPDAC_start/stop/step, etc.)
  CurrentState/      - live progress: current value being applied +
                       Done (bool) + Message (free text status)
  Running            - bool, is a sweep currently active
  Output/
    <swept quantity>/<index>/
      LV_Voltage[], LV_Current[], HV_Voltage[], HV_Current[],
      "Diode Temperature"[]
(CurrentCalibration itself currently reads "SmokeTest" - "IVScan", the
CalibrationExecute enum value, has never actually been run/written to
ODB. VDAC_power_consumption is a separate, real, working mechanism -
likely not even part of the current pixel_scripts codebase read this
session.)

FIRST DRAFT mirrored VDAC's Parameters/CurrentState/Running/Output
shape almost verbatim, then got dug through and deliberately trimmed
(user: "molte cose sono in comune con altri entry odb, mettiamo quello
che e' veramente nuovo") - every field below was checked against what
ALREADY exists elsewhere in ODB and kept only if it doesn't:

  DROPPED as redundant with existing ODB (would just duplicate data
  that's one query away already):
    - Feb crate/slot/link/firmware version - already in
      LinksFibre/Settings & FEBCrates/Settings, queryable by module/
      Feb name, no need to copy it into every calibration result.
    - RunNumber - already global at /Runinfo/Run number.
    - CurrentState/Voltage + Current (the "value being applied right
      now") - already live at /Equipment/HV/Variables/Demand[idx] and
      Current[idx], updated in real time by the real HV frontend -
      recomputing the channel index to read those is one lookup, not
      worth a duplicate copy that could go stale relative to the real
      readback.

  KEPT - each one genuinely does NOT exist anywhere else in ODB:
    - HVChannel - the module<->HV-channel mapping itself isn't written
      into ODB anywhere (only hardcoded in JS/soon Python) - this is
      the only place that traceability lives.
    - Status ("Running"|"Done"|"Aborted") + Message - "is THIS specific
      calibration attempt still going" doesn't exist anywhere else
      (raw HV/LV telemetry says nothing about calibration progress).
    - ParametersUsed/ - a SNAPSHOT of the parameters that produced this
      specific result (iv_start/iv_end/iv_step/settle_seconds/
      run_vbr_finding/fit_window_v/min_peak_prominence). Not redundant
      with the live ScanVbr/iv_start etc. the page writes to configure
      the NEXT run - those can be overwritten by a new configuration
      before this result is ever read, so without a snapshot the
      parameters that actually produced a given Output/Voltage[] would
      be unrecoverable. User confirmed: "snapshot i parametri dentro
      il risultato assolutamente."
    - Output/Voltage[] + Current[] - the actual measurement, the whole
      point of the calibration.
    - Output/Temperature[] - NOT redundant with the live SI1/SI2 in
      LinksFibre/Variables/SFFE despite reading the same sensor: SFFE
      is instantaneous and gets overwritten every readout cycle, this
      is a time series tied point-by-point to each scan step - a
      different piece of information than the live value.
    - VbrResult/ (Found/Confident/FitFailed/VBreakdownRaw/IBreakdown/
      VBreakdownFit/FitSigma - the full find_breakdown_voltage() return
      shape, calibrations/vbr_find.py) - entirely computed by this
      calibration, exists nowhere else.
    - Warnings[] - specific to this calibration run, not tracked
      anywhere else.

ODB vs CDB - WHAT EACH ONE IS FOR, agreed 2026-08-07 (user, explicit):
ODB is NOT a run database - it's an OPERATIONS database. It holds the
CURRENT/LATEST state only, nothing historical: the next ScanVbr on the
same channel resizes and overwrites Output/Voltage[]/Current[] outright
(same as VDAC_power_consumption's own Output/ behaves - last_written
timestamps update in place, no versioning). ODB answers "what's the
detector's calibration RIGHT NOW", not "what was it on run N". The
permanent historical record - every past run's calibration result, for
offline trending/analysis - belongs in CDB/RunDB instead (the 3rd
destination from step 6's RESULTS STRATEGY, ResultSaverRunDB - still an
empty stub in common/results/saver.py, not yet designed). Matches the
user's own original framing: "salvero' i dati in due parti in ODB e in
CDB" - two destinations, two different purposes, not the same data
duplicated for redundancy.

   Status="Done"/"Aborted" + VbrResult + Warnings at the end. Matches

ON STEP 4 - "PARALLELIZATION" ACROSS MODULES: since each module can now
carry its OWN iv_start/iv_end/iv_step/settle_seconds (per-row Start,
see the section above), a single shared voltage ramp across all
selected channels (what the real vbr_scan.py does today) no longer
fits once channels disagree on their own range. User asked whether this
needs real parallelization (threads/multiprocessing) - recommended NO:
each module already has its own independent HV channel/board, so real
OS-level parallelism buys nothing here and adds real risk (concurrent
ODB writes, the MIDAS client typically isn't thread-safe). Better fit:
a single-process STATE MACHINE - one loop, one tick per settle
interval, tracking each channel's own progress (current voltage,
remaining steps) in a dict keyed by channel, advancing only the
channels that haven't finished their own range yet, stopping a channel
once it's done while the others continue. More state to carry than
today's single shared loop, but no concurrency risk, still one Python
process, consistent with vbr_scan.py's existing shape.

Nothing here is implemented - this is purely the agreed shape for
whenever the real script gets written.
