WHY STEPS 2-7 DON'T PAY OFF (after reading the code, 2026-09-01)
-------------------------------------------------------------------
The roadmap's step 3 ("split SciFi bring-up into parallel units") is the
load-bearing assumption. It does not hold:

  - scifi/actions/poweractions.py build_lv_bringup_sequence(det) is ONE
    linear BringUpSequence of 6 detector-wide steps: tdk_scifi_tile
    verify -> dcdc_crates_enabled -> powerdist_crate_mains_on ->
    dcdc_crates_on -> powerdist_smb_ldo_on -> lv_channels_on. HV is 3
    more. Every step has wait_seconds=1, max_wait_seconds=5.
  - dcdc_crates_enabled / dcdc_crates_on are BULK ODB array writes:
    SciFiDetector.enable_all_dcdc_crates() writes
    /Equipment/DCDCCrates/Settings/Enabled = [True]*n, turn_on_all_dcdc_crates()
    writes Crate On = [True]*n. One write, the frontend brings up every
    crate. There is no per-crate / per-partition channel to pulse the
    way Pixel pulses one DCDC channel per partition.
  - the remaining steps already loop over all lv_groups / hv_groups
    in-process (fast ODB writes) then take ONE shared settle wait.
  - the steps are strictly ordered (can't turn crates on before
    enabling; can't turn LV channels on before the LDO). No reordering
    freedom.
  - worst-case LV bring-up ~= 6 * (1s + up to 5s) ~= 36s, typically
    ~6-12s. HV ~= 18s worst. Nobody parallelises a 10-second ordered
    sequence.
  - SciFiPowerPartitionBuilder builds raw group.PowerGroup (no
    SciFiPowerPartition subclass). The per-partition PowerGroups SciFi
    does build are used for status/monitoring and the calibration
    DCDC-crate-index checks, NOT as independent bring-up units.

Contrast Pixel: each of ~8+ partitions independently runs
PD -> LV -> VDD-ramp(interleaved with per-chip configure) -> HV, each
tens of seconds. Sequential = minutes, concurrent = tens of seconds.
That structure is why asyncio + ConcurrentEvents earns its keep there.
SciFi has none of it.

Building steps 2-7 for SciFi would add ConcurrentEvents +
configureRequired/configureDone plumbing for ZERO overlap, lose the
reversible BringUpSequence.power_down(), and lose the readable linear
step list. All cost, no benefit. Do NOT do it unless SciFi's bring-up
is first genuinely restructured into independent units (not currently
possible with bulk DCDC-crate control) AND there is a measured time
problem.


WHY NOT NOW (original note, still valid)
-------------------------------------------------------------------
1. Little to parallelise today - SciFi bring-up is one detector-wide
   sequence, not N independent units. Real parallelism needs the
   restructure in step 3 first.
2. No measured need - SciFi is far smaller than Pixel in channel count,
   ~6 steps, nobody has reported bring-up time as a problem.
3. MSCB serialisation (DCDC, Power Dist) applies to SciFi too - even
   parallelised, the power writes still queue behind the locks; only
   the waits/polls overlap.
4. The shared machinery is not production-ready -
   common/operation/concurrent_events.py is a stub (runForPP broken
   signature, runConcurrent calls fake_configure()); the working
   version is in pixel's unmerged feature/concurrency.
5. Async power sequencing on real hardware is a real risk surface -
   only worth it with a concrete operational pain point.

Do it only if: SciFi bring-up becomes a MEASURED bottleneck (cosmic-run
turnaround), AND the concurrent_events machinery is finished + proven on
Pixel first. Let Pixel be the guinea pig.


IF WE DO IT - ORDERED PLAN
-------------------------------------------------------------------

PREREQUISITE (not SciFi's job)
  Finish common/operation/concurrent_events.py: merge pixel
  feature/concurrency, harden it, prove it in a Pixel cosmic run.
  SciFi builds on it, does not battle-test it.

STEP 1 - refactor the shared async surface
  The generic helpers just moved onto PixelPowerPartition (_pulse_to,
  _wait_until, _set_lv_adjust, the locks, _log_* helpers,
  _lv/_pd_verified_on, _vdd_sense_exceeds_target) are NOT Pixel-specific
  in logic - only the turn_on_hv_and_verify / turn_on_lv_and_verify
  bodies are.
  -> Extract them into a common mixin, e.g.
     common/power/group.py :: AsyncPowerRoutines (a mixin beside PowerGroup, not a separate file).
  -> PixelPowerPartition changes from "owns the methods" to
     PixelPowerPartition(PowerGroup, AsyncPowerRoutines). Zero
     behaviour change for Pixel. This is NOT re-bloating PowerGroup -
     it is an opt-in mixin.

STEP 2 - SciFiPowerPartition(PowerGroup, AsyncPowerRoutines)
  Check first whether SciFi already has a PowerGroup subclass (builder
  currently uses raw group.PowerGroup). Create it if missing. Implement
  SciFi's turn_on/off_*_and_verify bodies - SciFi specifics (HVBoxP not
  HVBoxN, LV crate layout, tile TDK) - SAME SHAPE as Pixel, different
  body.

STEP 3 - split SciFi bring-up into parallel units  (the real design work)
  Today build_lv_bringup_sequence(det) is one detector-wide sequence.
  For concurrency to mean anything:
    - shared-prerequisite phase (TDK health, powerdist crate mains) -
      run ONCE, reuse the existing Step / BringUpSequence.
      Precedent: build_shared_feb_bringup_sequence.
    - per-partition phase - async def runForPP(self, pp, ...) doing one
      partition's PD -> LV -> HV, spawned in parallel over all
      partitions.
  The hard decision is the boundary between "shared, once" and
  "per-partition, parallel".

STEP 4 - rewire the SciFi action classes
  SciFiActionPowerOn / SciFiActionPowerOff:
  from  (SciFiActionBase)                    + .bring_up()/.power_down()
  to    (SciFiActionBase, ConcurrentEvents)  + async def runForPP
        + perform() = asyncio.run(self.runConcurrent(...))
  Mirror PixelActionPowerOn exactly.

STEP 5 - configure interleaving  (NEEDS SciFi input)
  Pixel threads configureRequired / configureDone events through
  runForPP because the VDD ramp interleaves with chip configuration.
  Does SciFi need to configure MuTRiG between LV steps?
    yes -> same event dance
    no  -> runForPP is simpler, no configure coroutine.

STEP 6 - what does NOT change
  - operation/bringup.py STAYS: used by the shared-prerequisite phase
    and by scripts/{lv,hv,feb}_bringup_run.py (manual/partial bring-ups
    for debug - keep them synchronous).
  - power-down: lose the "sequence reversed for free" property of
    BringUpSequence. runForPP for power-off hand-writes the reverse
    order (HV -> LV -> PD), same as Pixel. Cost accepted.

STEP 7 - tests + validation
  Async bring-up tests with fake supplies (precedent: pixel's
  test_parallelisation*.py). Dry-run mode must work. Then a real-
  hardware bring-up with someone watching, beam off.


EFFORT
-------------------------------------------------------------------
Steps 2-5: a few days of focused work + review.
Prerequisite: a dependency owned elsewhere (Pixel concurrency merge).
Step 7: hardware time, beam off.
Not something to slip in quietly.
