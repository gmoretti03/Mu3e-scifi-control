====================================================================

genuinely open, and in what order it makes sense to tackle it, for the
two calibrations scifi_scripts needs (threshold scan / scan_thr, IV
scan / scan_vbr). Nothing here is built - this consolidates reasoning
from 2026-07-22 into one place before any implementation starts.

1) THRESHOLD SCAN (scan_thr / calibrations/thr_scan.py)
====================================================================

1.1) Result saving - REMOVED, needs reviving with a clear head
--------------------------------------------------------------------
Built once (2026-07-21): ResultSaverRoot/ResultSaverODB/ResultSaverCDB/
ResultSaverMultiple, incremental per-step .root writing (not batch-at-
the-end, so a mid-scan crash doesn't lose completed steps). Removed the
same day, user's own call ("ci penserò poi") - not because it was wrong,
because it felt premature to lock in.
Hard requirement (Marius, confirmed): BOTH .root (current, ours to
build) AND CDB (delegated to whoever owns that piece - just needs a
real hook point in finalise(), not our implementation).
Destinations framework already sketched (code_design.txt 2.5's 5.9),
complementary not alternative:
  - local JSON/scratch - debug only
  - live ODB - real-time monitoring during a scan (transient)
  - RunODB - free per-run traceability
  - CDB - the offline-reconstruction destination (delegated)
OPEN: is the removed ResultSaver* architecture still the right shape,
or does today's granularity reasoning (1.3 below) change what "one
step's result" even means? If per-channel-independent ranges ever get
built, a step is no longer "one offset x one threshold for everyone" -
the incremental-write schema would need to carry per-channel state, not
just a flat step index. Worth deciding 1.3 before re-locking 1.1's
schema, not the other way round.
RESOLVED (confirmed 2026-08-21): ResultSaverROOT/CDB-based saving is
fully built (thr_scan.py/vbr_scan.py's build_root_report(), tested via
test_calibration_factory.py) - and the schema already accounts for

1.3) Granularity - today's real limitation, real precedent exists
--------------------------------------------------------------------
Today: ONE shared offset x threshold grid for every active, non-masked
channel - ScanThr.execute()'s loop has no per-channel/per-group range.
Real, working precedent for the redesign this would need: pixel's
VTX_iv_scan.msl (per-partition independent range + a shifter-selectable
mask + a loop sized by the longest range, shorter ones dropping out via
their own Done flag - see 2.3 below, same pattern applies here). Costs
nothing extra in scan time if done right (bounded by the longest range,
not the sum).
User's own framing (2026-07-22): should granularity follow the SAME
power groupings already built for the control page (US/DS for FEB/LV) -
i.e. per-Feb or per-US/DS threshold ranges, not a third, disconnected
grouping scheme. Agreed as directionally right in discussion - no
channel-order ambiguity blocks this for thr scan the way it does for HV
(channel->FEB mapping is already exact and known).

point 2, now archived): the granularity/grouping structure ALREADY

scan - is fine as-is, no redesign needed. Confirms the "User's own
framing" paragraph above was directionally right. Does NOT close the
underlying scan-mechanics gap (1.3's own opening paragraph - ScanThr's
loop still has no per-channel/per-group range today), just confirms

RESOLVED (confirmed 2026-08-21): ScanThr.execute() now scans per-ASIC
independent threshold/offset ranges (self.asics carries its own params
per folder, checked against its own range each tick) - the scan-
mechanics gap this section opened with is closed.

every SciFi HV channel, all swept together.

2.4) SAFETY GAP found 2026-07-22, not just a granularity nice-to-have

VTX_iv_scan.msl has a real over-current abort scan_vbr.py's loop has no
equivalent of: reads a configurable Max_Current_per_Chip parameter,
computes max_hv_current = that x n_chips, and cuts a partition's Demand
to 0 (marking it Done) if the measured current reaches that limit
mid-sweep. Checked whether HV's own frontend covers this the way it
covers voltage (mdev_hv4.cxx's real Voltage-limit clamp) - it does NOT:
HV/Settings/"Current limit" exists in the live ODB (confirmed,
docs/odb_220726_121718.json) but is only ever stored/displayed in
mdev_hv4.cxx, never compared against the measured Current. A real gap
to close whenever scan_vbr gets built for real, not something already
covered elsewhere.

FULL AUDIT + FIXES 2026-07-22, same day (user: "fai un check finale su vbr
e thr. un check completo e approfondito"): read every line of thr_scan.py/
vbr_scan.py/thr_find.py/vbr_find.py/feb.py/hv.py/scifi.py/calib_base.py/
calib_run.py/thr_run.py/vbr_run.py, plus the original rate_scan.py for
comparison. Found and fixed 3 real issues:
  1. BUG (safety-relevant): thr_run.py/vbr_run.py only printed
     calib.warnings via seq.msg() INSIDE the run_autofinding/
     run_vbr_finding conditional block - but the over-current warnings
     ScanThr/ScanVbr collect during execute() are independent of that
     flag. Since run_autofinding/run_vbr_finding default to False, an
     operator running with default parameters would NEVER see an
     over-current warning in the PySequencer log, even though the
     hardware-level mitigation (masking/demand-cut) DID happen - directly
     undermining the safety value of the checks just built. FIXED: the
     warnings loop now runs unconditionally, right after finalise().
  2. GAP: all 3 dispatch points (thr_run.py, vbr_run.py, calib_run.py's
     perform_calibration()) skipped finalise() entirely whenever
     execute() returned anything other than SUCCESS. For ScanThr this was
     theoretical (execute() never actually fails); for ScanVbr it's real -
     floating-point drift on voltage accumulation near the 60V cap
     (observed directly: 58.00000000000001 in our own test) could make
     set_demand_channels()/set_demand_all() reject the last step and
     return FAIL, skipping finalise()'s configure_alloff() and leaving the
     ASICs stuck in short-mode test configuration (or, for ScanThr, the
     switching board left bypassed - affecting every other subdetector
     sharing it). FIXED: finalise() (hardware cleanup) now always runs
     regardless of execute()'s outcome in all 3 call sites; the original
     failure result is still what gets returned/reported, cleanup just no
     longer gets skipped to do it. New regression test in
     test_calibration_factory.py (monkeypatches ScifiHv.set_demand_
     channels to force a failure, confirms MutrigConfigAllOff still fires).
  3. TEST REGRESSION (self-inflicted, found via the audit):
     test_calibration_factory.py's ScanVbr dispatch test never seeded
     Settings/"Current limit"[] for its HV channels, so today's own
     over-current check (see above) fell back to the mock's dummy 1uA
     limit against a mocked 1.5uA current - tripping on the very FIRST
     step and silently turning the test into a degenerate
     "all-channels-faulted-immediately" run instead of the real full
     sweep it was meant to exercise (confirmed: 186 "unhandled path" hits
     for Current limit during a debug run). Fixed by seeding a generous
     1000uA limit for all 6 mocked channels, same as test_vbr_scan.py/
     test_vbr_find.py already do.

3.2) CDB stays delegated either way
--------------------------------------------------------------------
Neither calibration needs its OWN CDB writer built here - both just

3.3) Result-saving schema should be decided AFTER the granularity
     question, not before
--------------------------------------------------------------------
Both 1.1 and 2.2 flag this: if per-channel/per-group independent ranges
ever get built, "one scan step" stops meaning the same thing for every
channel - the incremental-write schema (and the plot layout) would need
to account for that. Locking the saving format first and retrofitting
granularity later risks a second redesign.
