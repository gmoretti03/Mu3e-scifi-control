   - CDB/RunDB save mechanism (ResultSaverRunDB - still empty, distinct
     gap from ROOT, see step 6). CONCRETE DIRECTION FOUND 2026-08-09:
     read Docs/devolpment/Mu3e-Note-0133-CDB_RDB.pdf (Urs Langenegger,
     v2.0, 5 Aug 2026) end to end. The CDB actually hosts THREE distinct
     storage mechanisms, easy to conflate: (1) the real conditions
     database (/cdb, global tags/tags/payloads) - heavyweight, requires
     a dedicated calAbs-derived C++ class + schema + GT inclusion, meant
     for FINAL reconstruction-consumed constants, not a good fit for a
     WIP scan-result dump; (2) /detconfigs - opaque config file bundles
     (e.g. pixel mask/TDAC), grouped by string tag, NO run/IOV
     versioning; (3) /detcal ("Detector Calibration Files") - THIS looks
     like the right destination: arbitrary calibration-procedure output
     files (JSON/ROOT/binary), keyed by (name, run) with IOV-style
     lookup (largest stored run <= queried run, or exact=1 for an exact
     match), a simple REST API already built and documented with
     working curl/Python examples (POST /detcal/upload with file+name+
     run+optional comment/replace=1; GET /detcal/:name to list; GET
     /detcal/:name/:run to download; DELETE to remove). Much lighter
     than the real conditions DB - no schema class, no GT wiring. Two
     caveats found in the doc itself: the file-based CDB backend for
     /detcal isn't implemented yet (only the MongoDB-backed REST server
     works, at http://mu3edb0/detcal - fine, since a save mechanism
     would talk to that REST server directly anyway); and none of these
     routes enforce authentication. Not yet decided whether our
     "ResultSaverRunDB" naming should actually map to /detcal instead of
     RDB proper (RDB's runrecords are per-run bookkeeping documents,
     though they do support generic GridFS attachments via /rdb/
     addResource/:id) - /detcal's (name, run) IOV-style versioning is a
     closer conceptual match to "one saved result per scan run" than
     attaching to a run's own bookkeeping record. Still not implemented
     - this is a grounding finding, not a decision, and it's a real
     external system (mu3edb0) so any actual write there needs the same
     care as any other live-system action, not just a local ODB script.
