6. 2026-07-17: INCIDENT - stray MidasClient connections flooded
   mu3ebe's alarm log
----------------------------------------------------------------------
All live-ODB verification in sections 3-4 was done read-only via SSH
using ad-hoc midas.client.MidasClient('gm_check') connections, several
of which were not cleanly .disconnect()-ed at script exit. This left a
malformed /Programs/gm_check ODB record (struct-size mismatch between
what the python client writes and what mu3ebe's compiled C++ alarm-
checking code expects), which MIDAS's periodic alarm check (al_check)
then repeatedly tried and failed to repair, flooding the message log.
User fixed it directly on mu3ebe via
`odbedit -c "deldir /Programs/gm_check"`. Explicit instruction: never
do this again - saved as a standing feedback memory
(feedback_midas_client_disconnect): ad-hoc MidasClient connections for
quick reads must always disconnect cleanly (try/finally or
equivalent), never just exit after the last odb_get.


7. 2026-07-17: MAKING pixel_scripts' OWN TEST SCRIPTS RUN FULLY OFFLINE
----------------------------------------------------------------------
Trigger: user wanted to run pixel_scripts' test scripts locally (CERN
conda env) and assumed "if common/ is correct, no errors." Investigated
and found this assumption incomplete: TWO code paths ignored
is_odb_available entirely and would attempt a REAL MidasClient

class as the section 6 incident. Fixed both, with explicit user
approval (chose the more invasive option over "just fix the test
files"):

7.1) common/odb.py: ODBSelection.__init__ used to always call
   client.odb_get(key) for real. Now checks setup.is_odb_available
   first, falls back to odb_read_test(key) otherwise.

7.2) pixel_scripts/core/detector.py: Detector.__init__'s else branch
   (run_from_sequencer=False) used to ALWAYS create a real
   midas.client.MidasClient(...), regardless of is_odb_available. Now:
   if common_setup.is_odb_available, create the real client as before;
   otherwise self.client = None (nothing should call it directly in
   that mode).

7.3) pixel_scripts/core/feb.py: __update_chip_selection_mask_to_odb and
   __update_link_mask_to_odb called self.client.odb_set(...)
   unconditionally, with NO is_odb_available/can_send_commands_to_odb
   check at all (inconsistent with chip.py's equivalent set_to_odb,
   which already gated this correctly). Added the same gating pattern
   (real write if both flags allow it, otherwise odb.odb_write_test).
   Added `import common.setup as setup` to this file for it.

7.4) pixel_scripts/calibrations/calibrationfactory.py:
   get_calibration_to_perform_from_odb(client, odb_path) called
   client.odb_get(odb_path) unconditionally - no is_odb_available

   have crashed with AttributeError). Fixed to check is_odb_available,
   fall back to odb.odb_read_test(odb_path) otherwise. Added
   `import common.setup as setup` and `import common.odb as odb`.

7.5) pixel_scripts/test1.py, test2.py, test3.py, test4.py, test6.py:

   read_febs_from_odb lives in globals.setup) - a silent no-op that

10.1) HVBoxP vs HVBoxN resolved
   Mu3eSpecBook.pdf section 3.7 confirms SciFi's SiPM-bias HV boards are
   physically different hardware from pixel's (PSI-built Cockcroft-
   Walton positive generator, separate MSCB bus/fibre per side).
   However live odb.json shows Pixel/SciFi/Tile HV channels all share
   ONE /Equipment/HV tree with an identical field schema (Names, Output
   On, Enabled, Board, MSCB, Current limit, Demand, Current, Voltage) -
   cross-checked SciFi's channel range (idx 20-27) against pixel's, same
   fields/shape, differing only by a Board-name prefix (P/S/T =
   Pixel/SciFi/Tile) and the channel-name substring hv_power.py already
   filters on. User confirmed from domain knowledge: the write path is
   identical to pixel's, polarity is a hardware-level detail the board
   applies automatically. Conclusion: HVBoxNPowerSupply's existing ODB
   access pattern can be reused for SciFi's HV boxes as-is - no separate
   HVBoxP class needed at the ODB-interaction level. scifi_code_design.txt
   section 2.3 and todo.txt updated to reflect this as resolved.
