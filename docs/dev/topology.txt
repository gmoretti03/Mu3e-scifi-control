1) THE PHYSICAL CHAIN (spec book, chapter 6)
--------------------------------------------------------------------
  Fiber ribbon -> SiPM array (128 ch, Hamamatsu S13552-HRQ)
    -> SMB (SciFi Module Board, reads 1 SiPM array = 128 ch)
      -> 4 MuTRiG ASICs per SMB, 32 channels per ASIC (4x32=128, checks out)
    -> DAB (Detector Adaptor Board) - interfaces 2 SMBs to 1 FEB
    -> FEB (front-end board)

Counts (Phase I, final geometry):
  - 24 SMBs total: 12 upstream (US, numbered 0-11) + 12 downstream
    (DS, numbered 0-11)
  - 12 super-modules: 6 US + 6 DS (numbered 0-5), each holding 2 SMBs
    mechanically
  - 1 DAB per super-module (2 SMBs -> 1 DAB -> 1 FEB) => 12 DABs, 12
    FEBs total (6 US + 6 DS)
  - 8 ASICs per FEB (2 SMBs x 4 ASICs)
  - 32 channels per ASIC (fixed)
  - 256 channels per FEB, 3072 channels total in the detector
  - SMB3 (the version described in the spec book) hosts MuTRiG
    **version 3** ASICs, specifically. No MuTRiG2 mentioned anywhere in
    the spec book's SciFi chapter.

Unique 12-bit physical channel ID (spec book Figure 6.2):
  bit 11    : 0 = US, 1 = DS
  bits 10-7 : SMB number, 0000-1011 (0-11)
  bits 6-5  : ASIC number within SMB, 00-11 (0-3)
  bits 4-0  : channel number within ASIC, 00000-11111 (0-31)
  Example: channel 14 of ASIC 3 in SMB 7 upstream = 0 0111 11 01110

DAB is purely passive interconnect (equalizers DS25BR440, level
translators, no regulator) - it sits on/near the backplane between FEB
and SMB. It is NOT itself an addressable ODB entity anywhere (confirmed
independently by source B below) - treat it as physical/geometry
documentation only, not something Feb/Asic/Channel classes need to
model.


2) THE ODB/SOFTWARE-VISIBLE CHAIN (live-repo research, 2026-07-20)
--------------------------------------------------------------------
The C++ slow-control/frontend code models one level the spec book
doesn't name explicitly: "module" (= one SMB, in physical terms).

  Switching board "Fibre" (switch_id=3, real production board)
    -> FEB (up to 12, ODB-indexed via LinkFEB[]/FEBType[]==3)
      -> up to 2 "modules" per FEB (MAX_MODULES[Fibre]=2 - one SMB each)
      -> up to 8 MuTRiG ASICs per FEB total, flat-indexed 0-7 across
         both modules (NumASICsMax[] <= 8) - NOT reset to 0-3 per
         module in the ODB layer, unlike the spec book's physical
         per-SMB ASIC numbering. Whether ODB ASIC index (module*4 +
         asic_in_module) matches the physical per-SMB numbering 1:1 is
         a reasonable assumption but NOT independently confirmed -
         verify before relying on it in Asic class design.
         STILL OPEN, sharpened 2026-07-23 (real-world evidence from a
         Slack thread, Nicolas/bbuttwil/msakurai/mkoeppel, not our own
         research): a real historical mismatch exists - in 2025 the
         actual SciFi fibre cabling did NOT match the spec book
         (mkoeppel: "things are not as in the specbook since the fibre
         cabling ... was not correct"), and mu3eSort log values for
         FEB<->SM correspondence (US SM1->FEB144, DS SM1->FEB145, in
         their 1-indexed notation) didn't match specbook values either.
         2025 impact was masked because only one side was ever in data.
         For 2026 (bbuttwil: FEBs installed per specbook for the
         upcoming campaign - the one that actually matters, October
         2026), mkoeppel gave an independent derivation rule not
         currently used anywhere in this codebase: 96 total ASICs
         (48 US + 48 DS), FEBs mapped US-then-DS, per-FEB local ASIC id
         = global_asic_id % 8, FEB id = global_asic_id's own offset.
         CONFIRMED BY GREP 2026-07-23: this codebase (detector/*.py) has
         NO "global asic id" concept anywhere - Feb objects are built by
         trusting LinksFibre's own ODB array order for feb_index (0-11)
         directly, with position_in_feb just an enumerate() over
         NumASICsMax[feb_index], never cross-checked against any
         independent global-index derivation. The US-then-DS array
         order this code already assumes (feb_index 0-5 US, 6-11 DS,
         link_feb 144-149/150-155) happens to match the SHAPE of
         mkoeppel's rule, but this has never been verified against real
         2026 data - it's the same untested assumption as the paragraph
         above, just with fresh evidence that spec-book-vs-reality
         mismatches have already happened once for this exact mapping.
         NOT ACTED ON in code yet - the Slack thread was still open
         (Nicolas hadn't confirmed the DS SM1/FEB145 reading) when this
         note was written; don't build a global_asic_id abstraction
         speculatively before the real 2026 numbering is confirmed one
         way or the other.

         CONFIRMED, 2026-08-12 (user, directly, AND independently
         checked against the primary source - Docs/papers/
         Mu3eSpecBook.pdf, section 6.4.2 "Numbering convention" + Fig.
         6.2, pages 211-212): each SMB (=module) has a per-module
         hardware ASIC numbering 0-3 ("Bits 6-5: ASIC number", a 2-bit
         field), matching this codebase's own asic_in_module concept
         exactly. (Note: spec book section "7.1.4 ASIC numbering",
         page 222, same title, is NOT this - that one is SciTile's own
         section, a different subsystem; double-checked to avoid citing
         the wrong chapter.) No global_asic_id abstraction needed; the
         existing enumerate()-over-NumASICsMax[feb_index] approach
         stands confirmed against the spec book, not just
         "shape-matches" mkoeppel's rule. Closes this open question.
      -> 32 channels per ASIC (NMUTRIGCHANNELS, hardcoded constant in
         Mutrig_FEB.h/Mutrig3Config.h)

Every number above cross-checks exactly against source (A): 12 FEBs,
8 ASICs/FEB, 32 ch/ASIC, 2 modules/FEB = 2 SMBs/FEB. Strong
confirmation both sources describe the same real system.

3) MUTRIG2 VS MUTRIG3 - RESOLVED 2026-07-20 (Marius, direct reply:
   "No only Mutrig3. The mutrig2 is legacy code..." - CLOSED, no
   longer an inference)
--------------------------------------------------------------------
Source (A) describes SMB3 (final Phase I production board) as hosting
MuTRiG version 3 ASICs specifically. Source (B) separately found
wiki/SMB2.md describing an SMB2 (bench/lab-era board) hosting MuTRiG
version 2 ASICs, plus live software evidence
(Mutrig_FEB.cpp::SetupDB() branching on is_mutrig_3, MutrigConfiguration.html
swapping field sets, wiki/mutrig_settings.md documenting the exact
field diffs) that the DAQ software is fully generation-aware and
switchable per equipment-tree prefix.

Putting these together: MuTRiG2 vs MuTRiG3 most likely tracks SMB
board VERSION (SMB2 = lab/bench setups, still MuTRiG2; SMB3 = final
production, MuTRiG3), not a per-FEB or per-ASIC mix within one
deployment. is_mutrig_3 being a single flag per equipment-tree prefix
(not an array indexed per-FEB/per-ASIC) supports this reading - it
looks designed to toggle for an entire testbench/deployment at once,
not to describe simultaneous mixing.

CONFIRMED 2026-07-20 by Marius directly: SciFi is only ever MuTRiG3 in
real deployments. MuTRiG2 support in the software is legacy/dead code,
not a live concern - no mixing, ever, within any real deployment. Any
Feb/Asic/Channel class design work can safely assume MuTRiG3-only and
treat is_mutrig_3/MuTRiG2 handling as something to not actively
maintain (though not necessarily worth deleting outright, since it's
existing working code, not broken - just not a design constraint to
plan around going forward).

  - ASICsPerModule for those 2 active FEBs = 8, i.e. IDENTICAL to
    NumASICsMax (total per FEB), not 4 (which is what "per module"

    RESOLVES the section-4 contradiction: the field isn't unused (the
    wiki is stale) but it's also not really "per module" despite its
    name - it's populated with the FEB total, duplicating NumASICsMax.
    MutrigConfiguration.html summing it happens to produce the right
    total only because of this mislabeling, not because the field
    means what its name says.
  - Mapping/FEB<N> IS keyed by the global LinkFEB numeric value (decimal),
    not by feb_index: real data lives under "FEB144" and "FEB145"
    (=0x90, 0x91), not "FEB0"/"FEB1" (those exist too but are empty
    {} - stale leftovers from before real LinkFEB numbers were
    assigned, never cleaned up).
  - Mapping/FEB144 ("US SM 0") and FEB145 ("US SM 1") ASICChipIDs are
    flat sequential 0-7 (e.g. FEB144: 0x08..0x0f) - consistent with,
    but does not independently prove, the assumed module0=asic0-3/
    module1=asic4-7 split (section 2 above, still technically
    unverified for certain, though no evidence against it either).
  - LinkChipIDs for both active FEBs show a suggestive pattern: first
    4 entries are real distinct chip IDs, last 4 are an identical
    placeholder value (0x0063) - i.e. right now only ~1 of each FEB's
    2 possible modules (4 of 8 ASICs) appears to be physically wired
    with a real link chip ID, even though NumASICsMax/ASICMask report
    8 slots as logically available. Reads as further mid-assembly
    evidence (half-populated FEBs), not a contradiction of anything
    above.
  - SciFiFibre/Settings/Daq/is_mutrig_3 = 1 (a single scalar, not an
    array) - confirms the section-3 reading that this is one flag per
    equipment-tree prefix, not a per-FEB/per-ASIC array. Consistent
    with (doesn't prove or disprove) the "tracks SMB2-vs-SMB3 board
    version, not live per-FEB mixing" inference in section 3.

  CONFIRMED BUG (was previously just a flagged risk in todo.txt
  section 1): feb_power.py's feb_index <-> FEBCrate[]/FEBSlot[]
  mapping is WRONG, not just "unconfirmed". Evidence:
    - LinksCentral/Settings/LinkFEB[0:9] = 0,1,2,...,9 (rest 0xff/
      unassigned) - i.e. the global LinkFEB ID space starts at 0 for
      Central's own FEBs.
    - LinksFibre/Settings/LinkFEB values are 144-155 (0x90-0x9b) - a
      DIFFERENT, non-overlapping slice of that same global ID space.
    - FEBCrate[144:156]/FEBSlot[144:156] hold real, distinct,
      non-zero data (crates 0/2/5/7, varying slots) - i.e.
      FEBCrate[]/FEBSlot[] ARE indexed by the global LinkFEB value.
    - scifi_topology.py's get_scifi_febs() never reads LinkFEB[] at
      all - it only returns feb_index = local array position (0-11,
      from enumerate(feb_types)).
    - feb_power.py does febcrate[feb_index]/febslot[feb_index] with
      that LOCAL 0-11 index directly against the GLOBAL-indexed
      FEBCrate[]/FEBSlot[] arrays - i.e. for SciFi feb_index 0 it
      reads FEBCrate[0]/FEBSlot[0], which actually belongs to
      LinksCentral's FEB 0, not to SciFi's "US SM 1" (real LinkFEB
      145).
    Consequence: feb_power.py, run today against real SciFi FEBs,
    would compute the WRONG power_index and could toggle power on a
    crate/slot belonging to a different FEB entirely (possibly a
    different subdetector's). This is a real, live bug, not a
    hypothetical.

    FIXED 2026-07-20 (user gave explicit go-ahead to implement, not
    just flag): scifi_topology.py's get_scifi_febs() now also reads
    LinkFEB[] and returns it as "link_feb" per FEB dict (alongside the
    existing local "feb_index", kept for labels/other callers -
    additive change, doesn't break scan_thr/'s existing feb_index
    usage). feb_power.py now indexes FEBCrate[]/FEBSlot[] by
    feb["link_feb"] instead of feb_index, with an added bounds check
    (link_feb within array length) before indexing.

    Verified offline (no mu3ebe access) by replaying both the old and
    new indexing logic against the live odb.json dump: for ALL 12
    SciFi FEBs, old (feb_index) vs new (link_feb) crate/slot differ
    completely - e.g. feb_index 1 ("US SM 0"): old read (crate 1, slot
    0), new reads (crate 0, slot 11) - confirms the bug was systematic,
    not an edge case, and that the fix changes the result for every
    FEB as expected. Not yet run live on mu3ebe (dry_run=True still
    recommended for the first real run per README.md) - static/offline
    verification only, real PySequencer dry-run still worth doing
    before dry_run=False.

  Housekeeping note: the full ODB dump used for this check
  (docs/odb.json, ~46 MB) should NOT be committed to the Mu3e git repo
  - it's a raw data snapshot, not documentation, and 46 MB of live
  experiment state doesn't belong in version control alongside these

4d) DCDCCrates/FEBCrates - full readable/fault-flag inventory, found

  layout) is a per-crate telemetry block NOT related to FEBPower[]'s
